# Model Provider 重构回归用例目录

状态：第一版，待产品审阅

这份文档不是实现方案，而是给测试人员执行的用户场景目录。每条用例都包含：

- 用户能理解的场景；
- 测试前需要准备的数据；
- 用户实际操作；
- 应观察到的结果；
- 明确不应该发生的结果。

本版聚焦 **功能 × 功能**：新 Provider 代码与其他产品功能组合时的行为。老数据场景暂不放在本表，避免稀释功能交互的审阅重点。

`[待确认]` 表示这里还没有确定唯一产品预期，先把候选行为写出来，供产品审阅。

## 三、审阅时优先确认的预期

以下问题会改变大量功能用例的预期：

1. last-used 模型是全局生效，还是按 workspace 隔离？
2. Queue 消费时使用入队时模型，还是消费时当前模型？
3. 运行中切换模型是当前 Turn 继续用旧模型，还是立即中断并切换？
4. 切换到更小 context 时，是拒绝、自动 Compact、截断，还是新建会话？
5. 模型被删除、被禁用、鉴权失败、网络失败时，fallback 规则是否不同？
6. Start Plan、Coding Plan、API Key 切换时，在途请求和 Queue 分别使用哪种凭证？
7. Subagent、Compact、Title、Memory、Goal Verify、Automation、Wiki 是否继承主会话模型？
8. Git Commit 生成提交说明是否真的调用模型；如果调用，使用哪套模型规则？

Subagent 模型边界回放按父子请求身份及实际 `tool_result` 阶段匹配。提示词中的期望回复标记不表示子调用已完成；不得只靠该标记匹配 continuation，也不得把父请求中的 child prompt 计作真实 child 请求。

SR87-06 的旧自动化 fixture 在 Electron/Host 退出后同时回退该记录的旧字段与 `0002_provider_selection` 迁移记录，再冷启动验证真实迁移；只写 NULL 而保留完成日志并不代表旧版本前置。

F-OFFPEAK-002 使用隔离网关的确定性文本响应与请求记录场景：真实表单创建、取票和 scheduler 仍完整执行，验证 Team headers、ticket 与模型身份，不依赖真实上游或管理场景的排队窗口。
此例不能开启 `ZCODE_OFFPEAK_MOCK`：该开关会固定返回个人假凭证。网关由测试 launcher 独立启动，控制面代理票据请求并给出闲时曝光配置，Host 仍通过真实账号选择解析 Team 身份。
