# 扩展进程协议

设计见 `docs/plugins/extension-host.md`。本模块是扩展进程、Window Host、Renderer 三方共用的唯一定义，只含 schema、类型与纯函数。

- 清单校验分两步：先只读 `engines.zcode`（不兼容判 `incompatible`，不再看其余字段），再严格校验整个 `extension`（未知字段判 `invalid`，带字段路径）。
- 入口条目在清单顶层 `slots`（`manifestSlots.ts`），条目用 `target` 指向打开对象，`target` 只能有 `view`、`command`、`surface`、`tool` 中的一个键。未知插槽 id 忽略并记诊断；条目内的未知字段、超出上限、target 不被插槽接受、引用的视图或命令不可用，都只让该条目不可用（带字段路径）。
- `EXTENSION_SLOTS` 是插槽 id 的唯一定义，每个插槽声明它接受的 target 种类与每插件上限；插槽自己的条目字段写在 `itemFields`（`file.viewer` 的 `fileExtensions`），清单校验把它并进严格对象，别的插槽写了它按未知字段处理。P2c 起有五个插槽：`composer.status`、`sidePane.launcher`、`nav.primary`、`file.viewer`、`composer.mention`。插槽可以声明 `commandResult`：command target 返回值的 schema（`composer.mention` 用 `zcodePluginMentionItemsSchema`，与 CLI 共用）。静态表的 `file.viewer` 条目带小写去重后的 `fileExtensions`。
- 静态表（`staticTable.ts`）：唯一 owner 是 Window Host。`resolvePluginManifest` 把一个插件的 plugin.json 校验成静态表的一项（清单状态、可用条目、命令、视图、`main`、激活事件、问题与诊断）和扩展声明（只给合法、兼容的 extension；不含设置值，设置经能力 `settings.*` 读）。静态表带 `rev`，整份替换。
- 贡献表快照与增量共用 `rev`，每代际内单调递增，只含运行状态（`resolved`、`activating`、`active`、`failed`）与插槽动态值。`applyContributionMessage` 是接收方唯一的合入规则：新 gen 快照整份替换；增量必须同 gen 且 rev 更大，没有底稿的增量丢弃。
- 档位与协议（`grants.ts`，§17.3、§17.6、§17.7）：档位 `sessions.read`、`sessions.write`（write 包含 read，`grantCovers` / `grantsCover` / `normalizeGrants`）；能力表每行的 `grant` 是 `none` 或一个档位，可选 `protocol`（`sessions` 或 `rows`）。清单 `extension.grants` 与 `extension.protocols` 进静态表的 ok 扩展（档位去掉被覆盖的，协议没有声明时为空对象）；`isProtocolCompatible` 判断声明的版本是否等于 `EXTENSION_PROTOCOL_VERSIONS`。`EXTENSION_API_VERSION` 为 `1.3.0`（P3c 的写动作；各版本内容见 `manifest.ts`），类型包 `@zcode-dev/plugin-api` 的 version 与它相同。错误码另有 `not-granted`、`incompatible`、`forbidden`、`unavailable`、`conflict`、`cancelled`、`limit-exceeded`。
- 能力表 `EXTENSION_CAPABILITIES` 是能力的唯一定义；`ExtensionContext` 的能力部分由它推导（带入参的订阅生成 `(input, listener) => Disposable`）。会话 facade 的四个读 `sessions.listProjects`、`sessions.listSessions`、`sessions.readSession`、`sessions.waitSessions`（档位 `sessions.read`）直接用 session-control 的端口 schema。另有十二行：`context.get`、`context.onDidChange`、`models.onDidGenerate`、`workbench.visibleSessions`、`workbench.onDidChange`、`workbench.startDraft`（`workbenchStartDraftInputSchema`：`{ text, workspace? }`，`text` 非空白、最长 `WORKBENCH_DRAFT_TEXT_MAX_LENGTH`）、`env.get`、`env.onDidChange`、`views.open`、`settings.get`、`settings.onDidChange`（`settings.ts`：`{ values }`，只给调用方自己的插件）、`settings.update`（`extensionSettingsUpdateSchema`：`{ values?, clear? }`，至少一项，同一个键不能既写又清，键数与长度有上限；键是否属于 userConfig 由 Window Host 校验）。`LOCALLY_WRAPPED_CAPABILITIES`（`views.open`）的 ctx 入口在本地部分 `ctx.views.open`，先在扩展进程内校验视图 id 是否声明。
- 屏幕会话报告 `workbenchReportSchema` 与 App 环境 `extensionEnvSchema` 由 Renderer 产生；草稿多带 `draftModel`，扩展可见的形状 `workbenchSessionSchema` 不含它。
- 扩展视图：页面资源 URI 固定为 `ui://<pluginId>/<viewId>`；页面能转给视图 MCP server 的方法只有 `EXTENSION_VIEW_REQUEST_METHODS`。写法一的 `ViewDefinition.onDidOpen` 是实例的打开回调。`openView` 可带 `input`（`extensionViewInputSchema`：`{ kind: "file", path, workspace }`，path 是工作区相对的 posix 路径），扩展经 `ViewInstance.input` 读到；只有 file.viewer 打开文件时有。
- 日志控制台（`logs.ts`，§16.8）：条目 `extensionLogEntrySchema`（`seq`、`ts`、`level`、`gen`、可选 `pluginId`、不含文件前缀的 `message`）、快照 `extensionLogsSnapshotSchema`（带 Main 当前的 `lastSeq`）、上限常量与纯函数 `truncateExtensionLogMessage`（按 UTF-8 字节截断，加 `…[truncated]`）。控制消息：Main → Window Host 的 `extension-host/logs`（一批追加）与 `extension-host/logs-snapshot`，Window Host → Main 的 `extension-host/logs-request`，按 `requestId` 配对。
- 命令调用 `commandInvocationSchema` = Renderer 的 `{ commandId, scope }` 加可选 `args`；`extension-host` 频道的 `executeCommand` 返回命令的返回值（JSON）。`composer.mention` 的查询入参与结果在 `mention.ts`（`provideMentionItemsInputSchema`、`mentionItemsResultSchema`、`MENTION_ITEMS_ERROR_CODES`）。
- `extension-window` 频道只有 `call` 与 `onDynamicSubscribe`（subscribe）两个通用入口，不为单个能力加方法。`onDynamicSubscribe` 的事件是信封 `capabilitySubscriptionMessageSchema`（`event` / `error`），error 结束这次订阅；ctx 的订阅因此多一个可选的 `onError`（§17.3）。
- 会话读连接的投影（`sessions.ts`，§17.5、§17.6）：列表行 v1、列表事件、会话状态、完整行事件与 `readRows`，以及上限常量。静态表的插件项可带 `activation`（商店安装后等待确认或选择不激活，§17.7）。
- Jarvis 要的宿主能力（§18.1）：视图声明 `scope: "app"`（`extensionViewScopeSchema`，静态表视图带 `scope`）；扩展声明带 `dataPath`（来自 CLI 的 plugins/list，`ctx.extension.dataPath`）；能力 `models.list`（`extensionModelSchema`）；插槽动态值与补丁的 `badge`（`slotBadgeSchema`，正整数或 `"dot"`，目前只有 `nav.primary` 渲染）。档位 `notifications`（与会话档位互不覆盖，`isSessionGrant` 区分；启用确认只看会话档位）与能力 `notifications.show`（`notifications.ts`：入参、不弹的原因、限额常量、preload 与 Main 之间的载荷与点击）。
- 跨进程的形状不含函数、`AbortSignal`；需要取消的调用设计显式 cancel 方法。
- 给类型包 `@zcode-dev/plugin-api`（§17.9）的推导类型也定义在这里：`ExtensionCapabilityInput<K>` / `ExtensionCapabilityOutput<K>`（与 ctx 成员同一份推导，带请求身份的动作 `requestId` 可选）、`sessionActions.ts` 的 `SessionAction` / `SessionActionInput<A>` / `SessionActionResult<A>`（并转出 session-control 的三个会话引用类型）、`SessionRow`、`ManifestSlotTarget`、`ManifestSlots`。类型包只转出，不另写类型。
