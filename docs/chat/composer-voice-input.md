# Composer 语音输入

在 Composer 中点击麦克风说话，识别出的文字直接写入输入框。识别由 zcode-server 的 ASR 接口完成，协议见 zcode-server 仓库 `docs/asr.md`。本功能不修改 zcode-server 代码，只依赖其现有能力。

## 范围

- 第一版只支持桌面端（Electron）。Web 端和手机远控端不显示按钮。
- 只给已登录用户开放。未登录时不显示按钮；登录态变化后按钮随之出现或消失。
- 使用 `realtime` 模式，不指定 provider，由服务端 `default_provider` 决定。
- 识别语言跟随界面语言：`zh-*` 用 `zh-CN`，其他用 `en-US`（火山 realtime 只支持这两种）。
- 产品内不额外提示录音是否会被服务端留存。

## 入口

- 麦克风按钮在 Composer 右侧工具栏，位于发送 / 停止按钮左侧。图标按钮 `size="icon-md"`，lucide `Mic`，带 `ControlHintTooltip` 与 `aria-label`。
- 只在主 Composer 显示。用户消息的内联编辑框不显示。
- 录音中按钮扩展为一个胶囊（`rounded-full`，无边框，浅蓝底色 `bg-voice-input-surface`），左侧是音量波形，右侧是停止按钮：

  ```text
  空闲：            [🎤]
  连接中 / 识别中：  ( ··········· ◌ )   波形静止为最低档（圆点），按钮显示 Spinner
  录音中：          ( ·▎┃▍·▎·┃·▎·  ■ )   竖条高度随麦克风音量变化，按钮是停止方块
  ```

  - 波形 10 根 3px 宽的圆头竖条，总宽不超过按钮宽度的 3 倍。每根竖条代表一个 100ms 音频块的峰值，新数据从右侧进入、向左移动。音量按 -50 dBFS 到 -10 dBFS 映射为竖条高度：静音时是 3px 圆点，最大 14px。波形 `aria-hidden`。
  - 颜色使用 DESIGN.md 的 Voice Input Recording token（sky 色系）：胶囊底色 `--color-voice-input-surface`（浅色 sky-100 `#e0f2fe`，深色 sky-950 `#082f49`），竖条和停止方块 `--color-voice-input-wave`（浅色 sky-600 `#0284c7`，深色 sky-300 `#7dd3fc`）。不使用红色或 destructive 色，也不借用其他用途的 token。
  - 停止按钮是 ghost 按钮，内部是 `--color-voice-input-wave` 实心圆角方块。无障碍名称为「停止录音」。
  - 点击后胶囊从按钮向左展开：波形区域宽度从 0 过渡到内容宽度，同时底色和透明度渐入，时长 200ms、ease-out，左侧控件随之平滑移动。系统开启减少动态效果时直接显示。
  - 波形只在自身组件内更新（约每秒 10 次），不触发 Composer 重新渲染。系统开启减少动态效果时取消过渡动画。

- 工具栏空间不足时，按钮按 `composer-toolbar-layout` 规则压缩，不单独换行。

## 交互

1. 点击按钮开始录音。首次使用时 macOS 弹出系统麦克风授权。点击按钮不会让输入框失去焦点和光标。
2. 收到第一次服务端 `result` 时，在光标处插入识别文字（没有光标时追加到末尾），这段文字称为「语音文字」。之后每次 `result` 都用完整文本替换语音文字，不追加，光标保持在语音文字末尾。
3. 再次点击按钮结束录音。按钮进入"识别中"状态。采集端先 flush 出不足 100ms 的尾块并发送，之后再发送 `finish`，等待服务端 `completed`。服务端收到的音频字节数与采集字节数一致。
4. 收到 `completed` 后，用最终文本替换语音文字，语音文字变为普通文本。最终文本为空时删除语音文字。
5. 不自动发送。

### 用户开始输入或点击发送：与点击停止一致

录音中用户修改输入框内容（打字、输入法、粘贴、删除、撤销），或点击发送 / 按 Enter，都和点击停止按钮走同一流程：停止采集，发送尾块和 `finish`，等待服务端 `completed`，用最终优化后的文本替换语音文字。

用户开始输入时：

- 按钮进入「识别中」，之后到达的临时结果不再写入编辑器，用户可以继续打字。
- 收到最终结果后只替换语音文字本身。用户在语音文字末尾或其他位置输入的内容保留，光标不移动。
- 用户改了语音文字中间的内容时，最终结果不写入，保留用户版本。
- 首个识别结果到达前用户就开始输入时，最终文本插到录音开始时的光标位置（说话早于打字），光标不移动。开始位置之前的内容被用户改过（例如在它前面插入或删除文字），或开始位置所在的节点已不存在，都视为失效，此时追加到末尾。
- 不提示。

点击发送时：

- 先等最终结果写入编辑器，再读取草稿发送，发送内容是优化后的文本。
- 等待结束后按当时的最新状态发送：等待期间新增或移除的附件、网页元素等引用，以及连接是否可用、运行时是否被阻塞，都以等待结束时为准。连接已断开或运行时被阻塞时不发送。
- 等待期间按钮显示「识别中」，重复点击发送不会重复发送。等待时长受服务端 finish 超时约束（15 秒，GLM 为 40 秒）。
- 识别失败时按编辑器当前内容（已写入的临时文字）发送，并提示失败原因。
- 等待期间切换会话、切换工作区或 Composer 卸载：中止本次发送，不读取也不发送任何内容。原会话的临时语音文字留在其草稿里，用户可以回去重新发送。

只移动光标或选中文字不算修改，不影响录音。

判定方式：

- 用户修改会触发编辑器的非程序化更新（`onUserInputStart`），语音输入据此结束录音。
- 用户修改与识别结果写入在同一次编辑器提交中合并时，前者无法单独识别。写入前检查语音文字节点是否以上次写入的文本开头；开头部分被改过就拒绝写入，并按用户开始输入处理。
- 语音文字是独立的、不与相邻文字合并的文本节点。光标在语音文字末尾时继续打字，字符会追加进同一节点；写入时只替换上次写入的开头部分，用户追加的后缀原样保留。

撤销：第一次写入单独成为一条撤销记录，后续临时结果合并进这条记录。用户开始输入后写入的最终结果单独成为一条撤销记录，不与用户输入合并。

### 取消与结束

| 情况                              | 语音文字                               | 服务端              |
| --------------------------------- | -------------------------------------- | ------------------- |
| 点击停止                          | 替换为最终文本                         | `finish`            |
| 用户开始输入                      | 替换为最终文本，用户输入保留           | `finish`            |
| 点击发送 / Enter                  | 替换为最终文本后随消息发送             | `finish`            |
| 录音或识别中按 Escape             | 删除语音文字；用户在其后追加的输入保留 | `cancel`            |
| 切换会话、Composer 卸载、窗口关闭 | 保留临时文字（随草稿保存）             | `cancel` / 连接关闭 |

语音文字写入后会随草稿保存。应用在识别中途退出时，恢复的草稿就是用户最后看到的内容。

### 失败

所有失败都回到空闲状态，用 toast 提示用户（macOS / Windows 的权限被拒改用引导浮层，见「麦克风权限」），并写入后台日志。已写入的语音文字保留为普通文本。失败后不自动重试。

#### 麦克风权限

点击按钮后，先由 main 进程检查系统权限，再调用 `getUserMedia`。系统权限状态来自 `systemPreferences.getMediaAccessStatus("microphone")`，macOS 和 Windows 支持，Linux 不支持。

| 系统    | 判定                    | 处理                                                                                                                                             |
| ------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| macOS   | `not-determined`        | 调用 `askForMediaAccess("microphone")` 弹出系统授权。用户允许则继续，拒绝按 `denied` 处理                                                        |
| macOS   | `denied` / `restricted` | 显示权限引导浮层（见下文），提供「重新授权」和「打开系统设置」                                                                                   |
| Windows | `denied`                | 显示权限引导浮层，只提供「打开系统设置」（`ms-settings:privacy-microphone`）。文字说明需要同时打开「麦克风访问权限」和「允许桌面应用访问麦克风」 |
| Linux   | 无系统权限接口          | 不预检。`getUserMedia` 失败时按下面的设备错误处理，只用 toast 提示                                                                               |

系统权限显示已允许，但 `getUserMedia` 抛出 `NotAllowedError` 时，按该系统的 `denied` 处理（Windows 关闭「允许桌面应用访问麦克风」时可能出现这种情况）。

##### 权限引导浮层

macOS 的麦克风列表没有「+」按钮，只有请求过权限的 App 才会出现在列表里。用户点过「不允许」，或系统没有弹框就拒绝（签名身份变化、旧版本缺少 entitlement 等），`askForMediaAccess` 都不会再弹框。用户可能在设置页里找不到 ZCode。所以 macOS 提供「重新授权」：只重置 ZCode 自己的麦克风记录，再请求一次，让系统重新弹框。

浮层挂在麦克风按钮上（`Popover`，`bg-popover`、`rounded-xl`），不自动消失。点击浮层外部或按 Escape 关闭。浮层打开和关闭都不移动焦点：焦点和光标留在输入框，与「点击按钮不抢输入框焦点」一致。

```text
macOS                                                         Windows
┌──────────────────────────────────────────┐                  ┌──────────────────────────────────┐
│ 需要麦克风权限                            │                  │ 需要麦克风权限                    │
│ 点击「重新授权」，在系统弹框中选择「允许」 │                  │ 同时打开「麦克风访问权限」和……    │
│              [打开系统设置] [重新授权]    │                  │                    [打开系统设置] │
└──────────────────────────────────────────┘                  └──────────────────────────────────┘
```

「重新授权」的流程全部在 main 进程完成：

```text
renderer 点击「重新授权」
  │  IPC zcode:reset-microphone-access
  ▼
main：读取当前状态
  ├─ granted（例如用户已在系统设置里打开）───────────────▶ granted（不执行 tccutil）
  ├─ restricted（MDM 管控）──────────────────────────────▶ failed
  ├─ 打包版：/usr/bin/tccutil reset Microphone <bundle id> ── 失败 ─▶ failed
  │   （bundle id 读自当前 App 的 Info.plist；开发版跳过这一步）
  ▼
main：重新读取状态
  ├─ granted ───────────────────────────────────────────▶ granted
  ├─ not-determined ─▶ askForMediaAccess ─▶ 系统弹框 ─┬─ 允许 ▶ granted
  │                                                    └─ 拒绝 ▶ denied
  └─ 仍是 denied（当前进程仍沿用旧的授权结果）──────────────▶ restart-required
```

| 结果               | 浮层                                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------- |
| `granted`          | 关闭浮层，toast 提示「已开启麦克风权限」。不自动开始录音，用户再次点击按钮开始                          |
| `denied`           | 保持浮层内容不变                                                                                        |
| `restart-required` | 浮层改为「需要重启 ZCode」，提供「重启 ZCode」（`DesktopCommandIds.RelaunchApp`）。重启后点击按钮会弹框 |
| `failed`           | 打开系统麦克风设置页，浮层保持                                                                          |

- 只重置 ZCode 自己 bundle id 的麦克风记录，不影响其他 App 和其他权限。用户仍需在系统弹框中点「允许」，不会绕过用户的选择。
- 开发版（未打包）的 bundle id 是所有未改名 Electron 共用的 `com.github.Electron`，TCC 记录按路径保存，按 bundle id 重置无效，还会影响其他项目，所以跳过 `tccutil`，只做后面的状态判断。
- 是否需要重启由重置后的状态决定，不用超时或计时判断：仍是 `denied` 说明当前进程读不到重置结果。
- 已经是 `granted` 时不重置，避免删掉用户刚给出的授权。
- 重置在 main 进程串行：上一次「重新授权」还没结束时，后来的请求（例如分屏的另一个输入框）直接等待同一次结果，不会同时执行 `tccutil` 或请求系统授权。
- 开发版跳过 `tccutil`，状态仍是 `denied` 时同样返回 `restart-required`，但重启后仍是 `denied`。这只影响开发版；保留这条路径是为了让 E2E 能覆盖「需要重启」的浮层。
- 「重启 ZCode」失败时写 `warn` 日志，浮层保持。
- 浮层打开时，窗口重新获得焦点（`window` 的 `focus` 事件）就再检查一次权限。结果是 `granted` 时关闭浮层，并 toast 提示「已开启麦克风权限」。这是事件触发，不轮询。用户在系统设置里打开开关后回到 ZCode，浮层会自动关闭。
- macOS 在系统设置里修改权限后，当前进程有时仍读到旧状态。此时用户再点「重新授权」会进入 `restart-required`，重启后生效。
- 日志：main 的 `info` 记录重置结果（`reset microphone access result=…`），`tccutil` 失败记 `warn`。不记录 bundle id 以外的路径信息。

#### 设备与采集

| 原因                   | 判定                                                         | 提示                                                                                                                                                             |
| ---------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 没有麦克风             | `getUserMedia` 抛出 `NotFoundError` / `OverconstrainedError` | 未检测到麦克风，请连接麦克风后重试。macOS / Windows 带「打开声音设置」按钮（`x-apple.systempreferences:com.apple.preference.sound?input` / `ms-settings:sound`） |
| 麦克风被占用或无法打开 | `NotReadableError` / `AbortError`                            | 麦克风无法使用，可能被其他应用占用。macOS / Windows 带「打开声音设置」按钮                                                                                       |
| Linux 权限或设备问题   | Linux 下以上任一错误                                         | 同上文案，并说明检查 PulseAudio / PipeWire 输入设备。Linux 桌面环境没有统一的设置页地址，不显示跳转按钮                                                          |
| 录音中设备断开         | 音轨 `ended` 事件                                            | 麦克风已断开，本次识别已取消                                                                                                                                     |

#### 没有录到声音

renderer 在采集时统计本次录音的峰值电平。结束录音时按以下规则判断，判断后不再等待或丢弃服务端结果：

| 原因                 | 判定                                                                 | 提示                                                                                           |
| -------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 采集到的全是数字静音 | 所有采样值为 0                                                       | 没有收到麦克风声音。通常是系统权限未开启或选错了输入设备，带「打开系统设置」按钮（同权限一节） |
| 音量过低             | 峰值低于 -50 dBFS                                                    | 没有检测到声音，请检查麦克风是否静音或离得太远                                                 |
| 录音时间过短         | 发送的音频少于 300ms，或服务端返回 `empty_audio` / `audio_too_short` | 说话时间太短，请重试                                                                           |

以上三种情况都向服务端发送 `cancel` 结束会话，不等待识别结果。已写入的语音文字保留。

#### 没有识别到内容

声音正常，但服务端 `completed` 的文本为空（trim 后）：提示「没有识别到内容，请靠近麦克风再说一次」。

#### 服务端失败

| 阶段                        | 原因                                            | 提示                                                                                                                                                                                     |
| --------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 申请 ticket                 | 网络错误、超时                                  | 无法连接语音识别服务，请检查网络                                                                                                                                                         |
| 申请 ticket                 | HTTP 401 `unauthorized`                         | 不单独提示。ticket 请求经 `NodeApiClient` 携带当前 `zcodejwttoken`，401 会进入全局登录失效流程：清理登录态并弹出「登录已过期」对话框，对话框中有登录按钮。登录态清空后麦克风按钮随之隐藏 |
| 申请 ticket / WS 事件       | `rate_limited`、无响应体的 429                  | 语音识别繁忙，请稍后再试                                                                                                                                                                 |
| 申请 ticket / WS 事件       | `unavailable`、`upstream_unavailable`、HTTP 503 | 语音识别服务暂不可用，请稍后再试                                                                                                                                                         |
| WS 事件                     | `upstream_timeout`                              | 语音识别超时，请重试                                                                                                                                                                     |
| WS 事件                     | `audio_limit_exceeded`                          | 已达到单次录音时长上限，已识别的文字已保留                                                                                                                                               |
| WS 握手成功后、`started` 前 | 经 HTTP 代理，连接非正常关闭（未收到 close 帧） | 无法通过 HTTP 代理连接语音识别服务。请确认代理支持 WebSocket，或把服务地址加入「不使用代理的地址」后重启应用                                                                             |
| WS 握手                     | 失败（含 403）                                  | 语音识别失败，请重试                                                                                                                                                                     |
| WS                          | `completed` 前连接断开，或其他错误码            | 语音识别失败，请重试                                                                                                                                                                     |

代理一行的依据：WS 握手成功（`onopen`）后、`started` 前，服务端的失败路径一定先发 `error` 事件，再发 close 帧（1011）。客户端两者都没收到、只看到非正常关闭（1006），说明帧在中间被丢弃。经代理时，中间节点就是代理。实际案例：用户设置本地 MITM 抓包代理（自定义 CA），ticket 请求成功，WS 每次约 5 秒后 1006 断开，与服务端 start 5s 超时一致。是否经代理由 Host 网络 transport 建立 WebSocket 时的选路结果决定，不由语音输入另行判断。握手失败不属于这一行：服务端在握手阶段用 HTTP 状态拒绝（ticket 无效、Origin 不允许等，例如 403），客户端只看到 1006，且没有状态码，无法判断是代理还是服务端拒绝，所以即使经代理也按「语音识别失败，请重试」处理。Host 使用 undici 6 的 WebSocket，握手被拒时只触发 `error`、不触发 `close`，所以握手前的 `error` 就直接结束本次识别（日志 `stage: "handshake"`），不等待 `close`。`started` 之后的断开和直连时的断开同样按通用失败处理。

#### 日志

每次失败写一条日志，便于按 `attemptId` 和服务端 `session_id` 排查。

- Host（`createServiceLogger("voice-input")`）：
  - `info`：会话开始（attemptId、语言）、WS 握手成功（`socket open`：attemptId、是否经代理、耗时）、会话结束（结果类型、耗时、发送字节数、`audio_duration_ms`、服务端 `session_id`、`provider`）。
  - `warn`：可恢复失败，例如 ticket 请求失败（HTTP 状态、`error_code`、`logid`）、WS 错误事件（`code`、`retryable`）、`completed` 前断开（close code、`wasClean`、是否已握手成功 `opened`、是否经代理 `viaProxy`）。`opened=false` 表示握手失败（`stage: "handshake"`）；`opened=true` 且没有 `started` 表示握手后连接被断开（`stage: "socket"`）。
  - `debug`：每个音频块、每次 `result` 的长度，以及 Host RPC 中间件对 `voice-input.sendAudio` 的逐次成功日志（`packages/desktop/src/host/rpcLogLevel.ts`）。`sendAudio` 失败、`start` / `finish` / `cancel` 仍按原级别记录。
- UI（`packages/ui/src/logger.ts` 的 `logger.lifecycle`，生产构建也会落盘；普通 `logger.*` 在生产构建是 no-op）：开始（attemptId、系统权限结果）、失败（分类、`getUserMedia` 错误名、阶段）、采集结束（峰值电平、时长、采集字节数）、取消与停止原因（Escape、发送、用户输入、语音文字被修改）、完成（文本长度）。每次录音只有几条。
- 日志不记录识别文本、音频内容、ticket 和 JWT。

## 状态机

```text
                         result：替换语音文字
                              ┌──┐
idle ──点击──▶ requesting ──started──▶ recording ──点击 / 用户输入 / 发送──▶ finishing ──completed──▶ idle（最终文本替换语音文字）
                  │                         │                                   │
                  ├── Escape ───────────────┴───────────────────────────────────┴──▶ idle（删除语音文字）
                  └── 失败 / 切换会话 ──────────────────────────────────────────────▶ idle（保留语音文字）
```

- 语音文字的唯一 owner 是编辑器 handle：它记录语音文字节点和上次写入的内容。语音输入 hook 只调用「替换语音文字」和「结束语音文字（删除或保留）」两个操作。

- `requesting`：申请麦克风权限、申请 ticket、建立连接、等待 `started`。此阶段已经开始采集音频，采集到的音频先缓存，收到 `started` 后按顺序发送，避免丢掉开头的话。
- 每次录音有一个 attempt id。旧 attempt 的事件到达时直接丢弃，避免快速重复点击造成串话。
- 状态只由本地操作和服务端事件驱动，不额外加客户端超时。服务端有 start 5s、idle 15s、finish 15s 的超时，到期会发出错误并断开。
- 同一时间只允许一个识别会话。

## 链路

```text
Renderer（packages/ui）                       Window Host（packages/services）           zcode-server
  getUserMedia → AudioWorklet
  → 16kHz 单声道 PCM16，每 100ms 一块（3200B）
  start(attemptId, language) ───RPC───▶ POST /api/v1/asr/tickets {mode:"realtime"} ─────▶ (Bearer zcodejwttoken)
                                         WS /api/v1/asr/realtime?ticket=… ────────────────▶
                                         send start{pcm_s16le,16000,1,language}
  ◀──────── onEvent(started) ──────────── ◀ started
  sendAudio(attemptId, Uint8Array) ─────▶ binary ──────────────────────────────────────────▶
  ◀──────── onEvent(result 全量文本) ───── ◀ result
  finish(attemptId) ────────────────────▶ finish ──────────────────────────────────────────▶
  ◀──────── onEvent(completed) ────────── ◀ completed → close 1000
```

- WebSocket 在 Host 进程中建立。原因：生产环境 renderer 来自 `file://`，浏览器会带上 `Origin`，服务端只接受 `allowed_origins` 中的 http(s) 来源；Node 端连接不带 `Origin`，服务端按原生客户端放行。
- ticket 只能用一次，60 秒内有效。每次录音都重新申请。
- WebSocket 与 ticket 请求走同一个 Host 网络 transport（`createHostApiNetworkTransport` 的 `createWebSocket`）：使用设置中的 HTTP 代理、No Proxy 与自定义 CA，`ws://` 按 `http`、`wss://` 按 `https` 选路；代理配置无效或 CA 读取失败时直接失败，不回退直连。连接复用 transport 的 dispatcher，transport 释放时一起关闭。`createWebSocket` 同时返回本次连接是否经代理（`viaProxy`），供失败分类和日志使用。
- 采集在 renderer 中进行，通过 RPC 把 `Uint8Array` 传给 Host。同一 RPC 通道按调用顺序送达，所以尾块的 `sendAudio` 一定在 `finish` 之前。
- UI 只依赖传输接口（start / sendAudio / finish / cancel / onEvent），不感知 WebSocket。桌面端注入 Host 实现；其他平台不注入，按钮不显示。

## 平台要求

- macOS `Info.plist` 声明 `NSMicrophoneUsageDescription`。
- macOS entitlements 声明 `com.apple.security.device.audio-input`（hardened runtime 下缺少该项会采集到静音）。
- 权限检查、授权请求、重新授权和打开系统设置页都在 main 进程完成，renderer 通过 `IPlatformService` 的可选能力调用。各系统的处理见「失败 / 麦克风权限」。打开设置页只允许本文列出的固定地址；重新授权只执行固定的 `/usr/bin/tccutil reset Microphone <当前 App bundle id>`，renderer 不能传参数。

- 已登录桌面端显示按钮；未登录、Web、手机远控端不显示。
- 用假音频设备输入一段语音：识别结果直接出现在光标处，结束后替换为最终文本，不自动发送。
- 录音中按 Escape：语音文字删除。录音中打字、点击发送：与点击停止一致，等最终文本替换语音文字（发送时再发出）。切换会话：保留临时文字，服务端收到 `cancel`。
- 录音中按 Cmd/Ctrl+Z：整段语音文字一次撤销。
- 服务端返回错误或在 `completed` 前断开：回到空闲并提示。

- 每种失败在 Host 或 UI 日志中有一条记录，日志中没有识别文本和凭据。
- 深浅两套主题、中英文界面下按钮显示正确。
