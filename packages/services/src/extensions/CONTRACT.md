# 扩展门面（Window Host）

设计见 `docs/plugins/extension-host.md` §3.4、§3.5、§13。

- 插件访问 App 的唯一适配层。业务服务不知道插件存在；能力只经能力网关（`capabilityGateway.ts`）：查表 → 校验入参 → 清单声明的档位（`not-declared`）→ 声明的协议版本（`incompatible`）→ 用户授权（`not-granted`）→ 审计 → 分派。网关按连接（扩展进程代际）创建，调用上下文带 `{ pluginId, gen }`。处理函数表写成 `satisfies CapabilityHandlerMap`，少一个能力就编译失败。审计：调用按 debug 记一行，订阅记开始与结束，不记入参与事件内容。
- 会话能力（`sessionsBackend.ts`，§17.2、§17.3，① 调现有服务）：`AppControlService` 由 `createLocalServices` 的 `onAppControlServiceCreated` 交进来（依赖 `appControl`），不在任何 RPC 频道上。每次调用以客户端类调用方 `bindClient`（`clientId = extension:<pluginId>`，`connectionId = extension-host:<gen>:<pluginId>`），`assertCurrent` 检查代际与授权，结束时再查一次（换代 `cancelled`、撤销 `not-granted`）。session-control 错误码按名映射，其余 `internal`（日志只记错误类型）。换代或断开中止全部在途调用，撤销中止该插件的；每插件同时最多 4 个 wait。
- 插件项目（`pluginProjects.ts`，§17.4，P3c-2）：`sessions.createSession` 不带 `project` 时，在 `sessionsBackend.run` 的调用里先找插件项目再进 facade，之后与带 `project` 的调用完全相同。插件项目是本机未删除、roots 含 `<dataPath>/workspace` 的项目（`dataPath` 来自扩展声明，H6），没有就经依赖 `projects`（本机 `IProjectService`）的 `saveProject` 新建，名字是静态表里的插件名。项目库是唯一事实源，不另存映射；本模块不碰数据库。每次都 `mkdir -p` workspace；同一插件同时只有一次在途。
- 会话读连接（`sessionReads.ts`、`sessionListPump.ts`，§17.5，P3b）：列表泵读 Window Host 宿主注入的控制器投影（依赖 `taskRows`，只在本进程内），有订阅者时才订阅，映射成列表行 v1 后按行比较，snapshot 之后推 delta。正文按会话共享镜像：每个扩展进程代际一个连接作用域（`extension-host:<gen>`，`web-remote-replayable`，进程内握手），`detach` 时 `scope.dispose()`；会话目标经 facade `readSession(view: summary)` 解析（与模型工具同一份授权，只读本机来源）；snapshot → reset，deltas → apply 后的整行，断档或组装失败 → forceSnapshot 重同步，会话重启或运行时重启 → 重新订阅。上限：每插件 8 个不同会话、全局 32 个镜像（`limit-exceeded`），镜像 8 MiB（丢最旧的行），单个事件 1 MiB（`stale`）。`readRows` 经同一作用域调 v4 `rows/range`。帧与增量只记 debug。
- 订阅的错误（§17.3）：`onDynamicSubscribe` 的事件是信封，准入被拒、后端 `fail`、授权撤销都以一条 error 结束订阅。网关按连接监听授权状态与静态表的变化，复查开着的需授权订阅。
- 商店安装后的激活确认（§17.7，P3b）：`install` 成功后新出现、带扩展代码的插件，在已有别的插件持有生效会话权限时记为 pending（`grants.json` 的 `activations`）；pending 与 declined 不进扩展声明，静态表的这一项带 `activation`。授权门面的 `decideActivation` 决定激活或不激活，与静态表重读同一条串行链；user 层 `enable` 与卸载删除记录。
- 三块后端：① 调现有服务 `settingsBackend.ts`（能力 `settings.*`，§16.7：读 Window Host 进程内的 `plugins/readUserOptions` 读取器，只给调用方自己的插件；旧 CLI 只有 `plugins/list` 的非敏感值并 warn 一次；插件管理服务的成功信号带 `{ action, pluginId, scope }`，user 层的 `configure` / `reset_config` 通知该插件的订阅者，串行先读后推；`settings.update`（§18.1 H1）按本插件 `plugins/list` 的 `userConfig` 校验键与值类型后，经同一个 `IPluginManagementService.configurePlugin` 写 user 层，成功信号照常触发通知；日志不含值）；② 数据泵 `contextPump.ts`（context 组成：转发 CLI 的修订号通知，草稿换模型时补发；查询时草稿带报告里的所选模型，正式会话不带）与 `generationPump.ts`（生成速率：stream.chunk 估算 + model.request.metrics 准确值，只统计主轮，没有订阅时不聚合）；③ Renderer 报告 `workbenchState.ts`（只持最近一份）与视图中转 `viewRelay.ts`（准备实例、按实例转发请求与通知、登记 `contentKind: "extension"` 沙箱、views.open 请 Renderer 打开并等回执）。数据泵只订阅报告里出现的工作区。
- 按代际连接扩展进程：Main 牵线的端口到达即替换旧连接；只持最近一份贡献表快照（运行状态与动态值，`applyContributionMessage`），不维护第二份。扩展进程不在运行时丢弃快照并告诉 Renderer `detached`。视图声明从静态表查（`viewRelay.ts`）。
- 静态表（§16.1）：本服务是唯一 owner。`listPlugins({ configScope: "user" })` 中用户级启用、包已物化的插件，逐个异步读 `plugin.json`（`manifestReader.ts`，候选目录与 CLI 同序），用协议模块的 `resolvePluginManifest` 校验，生成带 `rev` 的整份静态表推给 Renderer（与贡献表同一条流 `onDynamicContributions`，消息 `kind: "static"`，订阅时先收），只把合法、兼容的扩展声明推给扩展进程（`setDeclarations`）。启动、插件管理操作成功（信号由 Host 的插件管理服务产生，不由 Renderer 回传）、「重新加载扩展」时重读；每次牵线后推一次当前声明。重读与推送串行，扩展进程总是收到最新一份。扩展进程停止时静态表照常。
- App 环境（§16.11）：Renderer 经 `reportEnv` 报告界面语言，`envState.ts` 只持最近一份；能力 `env.get` 在没有报告时抛 `host-unavailable`，`env.onDidChange` 订阅后先收当前值。
- 扩展进程状态的 owner 是 Main 的监管器，本服务只转发。`reload()` 经 parentPort 请 Main 重启，不经扩展进程。
- 日志控制台（§16.8）：缓冲的 owner 也是 Main 的监管器。`onDynamicLogs` 转发 Main 每轮事件循环推来的一批；`getLogs({ sinceSeq? })` 经 parentPort 发 `logs-request`，按 `requestId` 等 Main 的 `logs-snapshot` 回包后原样返回。本服务不留副本，销毁时在途请求失败，没有超时。
- 两个门面，同一个实现与同一份状态：`IExtensionsService`（`contract.ts`：插槽数据、扩展进程状态、命令、重新加载、Renderer 报告）与 `IExtensionViewsService`（`views/contract.ts`，频道 `extension-views`：视图实例、页面请求与通知、views.open 的请求与回执，以及 `workbench.startDraft` 的请求与回执）。拆分是为了守住每个契约 12 个公开方法的门禁；新方法按意图归到已有门面，授权例外（见下）。
- 授权（§17.7、§17.8）：`grantsStore.ts` 是 `~/.zcode/v2/extensions/grants.json` 的唯一 owner（`{ version: 1, plugins: { <pluginId>: { grants, consentedVersion, consentedAt, consentRevision? } } }`，原子私有写，串行，异步读，读不懂时备份并按没有记录处理）。生效档位只按「记录 ⊕ 最近一份静态表」现算：清单声明的档位都被记录覆盖、且声明覆盖 `sessions.write` 时记录的 `consentRevision`（缺省 1）不低于 `EXTENSION_SESSION_CONSENT_REVISION` 才生效，否则 needs-consent（会话能力报 not-granted，§17.12）；授予时写当前 revision。静态表重读先等记录读完，再 `reconcile`：声明没超出记录 → 静默记下新版本；声明变多 → 待授权、记录保留；声明变少 → 自动收窄；生效档位变少的插件中止在途调用。授予与撤销按「写文件 → 审计行 → 发布」提交，写文件失败时恢复内存记录并抛错。卸载删除记录（插件管理成功信号 `uninstall`），禁用不删（状态 inactive）。`auditLog.ts` 写 `audit/<本机日期>.jsonl`，串行追加（0600），日期变化时清理 30 天以前的文件，不用定时器；P3a 只有授权与撤销两种行（`grants.grant` / `grants.revoke`），不写内容。
- `workbench.startDraft`（§18.1 H2，`draftRelay.ts`）：照 views.open，经 `onDynamicDraftRequests` 请 Renderer 开预填草稿，等 `ackDraftRequest`。回执只表示窗口已接手，不等草稿准备完。没有订阅者时直接 `host-unavailable`，最后一个订阅者退订时在途请求失败，不用超时。日志只记插件 id、文字长度、是否指定工作区与回执结果。
- 第三个门面 `IExtensionGrantsService`（`grants/contract.ts`，频道 `extension-grants`）：`onDynamicGrants`（先收当前一份）、`grant`（档位必须等于清单当前声明，否则拒绝）、`revoke`、`describeEnable`（已有别的扩展持有生效权限、且目标插件带扩展代码时 `confirm`）、`getRecentActions`，P3b 的 `decideActivation`（商店安装后的激活确认），P4 的 `onDynamicGrantRequests` / `ackGrantRequest`（能力 `grants.request`，§18.1 H12）与 `setNotificationsEnabled`（详情页「系统通知」开关，§18.1 H8），共 9 个。授权是一组独立的意图，放进 `IExtensionsService` 会超过 12 个方法，所以单独一个频道（与上一条「不新开第三个频道」的约定不同，P3a 决定）。扩展进程没有授予自己权限的入口。
- 只在桌面本机 Host 注册；Web 与手机远控不提供这三个频道（不在手机白名单里）。
- `prepareView` 可带 `input`（file.viewer 打开文件时，§16.5），按协议的 `extensionViewInputSchema` 校验后经 `openView` 交给扩展进程。
- 视图实例属于一代扩展进程：换代或断开时全部作废。不为单个视图请求设计取消，关闭实例即取消在途请求。
- `composer.mention`（§16.6，`mentionItems.ts`）：`provideMentionItems({ entry, query, scope, seq })` 只认静态表里该插槽的可用条目。command 条目调扩展命令（`args: { query }`），返回值按 `EXTENSION_SLOTS["composer.mention"].commandResult` 校验；tool 条目要会话作用域，调 `IZCodeAgentService.getPluginMentionItems`（CLI plugins/mentionItems，会话的授权链）。结果是 `{ seq, status: ok | unsupported | error }`，错误折成稳定码，不抛给 Renderer。不设计取消，seq 原样带回。日志不记 query 与候选内容。
