# 数据同步：把本机配置推送到远端设备

Status: ready-for-agent

本规格基于设计稿（`design/data-sync-demo` 分支的静态 Demo 与 `docs/remote-sync-static-demo.md`）以及 2026-10-16 的方案评审。设计稿是 UI 静态预览；本规格只实现其中与设备同步相关的部分，并按评审结论收窄范围。设计稿以外的取舍都在「实现决策」中写明原因。

## Problem Statement

用户在本机配置了技能、MCP 服务器、插件、子智能体、命令和钩子。连接 SSH、WSL 或 Docker 远端设备后，远端 Agent 只读取远端自己的 `~/.zcode`，本机配置在远端不生效。现状有以下问题：

- 只有技能、MCP、插件三类可以手动同步。入口分散在 6 处，对应 3 个不同的弹窗。
- 现有同步只能新增。同名项一律跳过，用户无法更新远端已有的项，也看不出两端是否一致、哪一端较新。
- 子智能体、命令、钩子没有任何同步方式。本机写好的配置，在远端只能手工复制。
- 没有按设备查看"本机与远端相差多少"的总览，也看不到上次同步的时间和结果。
- 设置页的 Scope 菜单在远程场景下，User 级的归属规则不一致：子智能体固定写本机，命令、钩子、技能、MCP 跟随当前 workspace。用户看不出自己正在修改哪台设备的配置。
- 模型配置由 Provisioning 自动下发。连接建立后如果下发失败，界面上没有任何反馈，用户也无法重试。

## Solution

在「设置 → 数据与统计」下新增「数据同步」页。页面列出本机已知的远端设备。用户在设备行上点「同步」，打开该设备的数据同步弹窗。

弹窗左侧是分类导航。「概览」比较每一类数据在本机和远端的数量与差异；各分类页列出本机的条目，并标出每一项相对远端的状态：

- 只在本机：推送。
- 本机版本较新：更新。
- 远端较新或内容不同：差异。
- 两端一致：已同步。

用户勾选后推送到远端。推送永不删除远端独有的条目。远端较新或内容不同的项默认不勾选，用户可以主动勾选并覆盖。

模型提供商分类只读：它显示自动下发的状态，失败时提供重试。原有的 6 处同步入口保留，统一打开这个弹窗。各设置页的 Scope 菜单改为按设备分组，并显式标出设备名。原「Onboarding」入口移到本页的「迁移数据」按钮。

```text
设置 → 数据与统计 → 数据同步（仅桌面端）
 ├─ [迁移] ─────────────▶ 迁移向导第一步（从其他 AI 工具导入本机）
 └─ 设备列表（SSH / WSL / Docker）
      └─ [同步] ─────────▶ 数据同步弹窗（本机 → 远端）
            ├─ 概览
            ├─ 模型提供商（只读）
            ├─ 子智能体 · 插件 · MCP 服务器 · 技能 · 命令 · 钩子
            └─ （会话、记忆：本期隐藏）
```

## User Stories

### 设备列表

1. 作为桌面端用户，我希望在「设置 → 数据与统计 → 数据同步」中找到同步功能，以便有一个固定位置管理多台设备的配置同步。
2. 作为桌面端用户，我希望设备列表列出本机已知的 SSH、WSL、Docker 设备，以便同步时不需要先打开某个远程项目。
3. 作为桌面端用户，我希望每台设备显示状态点、名称、传输方式、目标地址和上次同步状态，以便快速判断哪台设备需要同步。
4. 作为桌面端用户，我希望看到「今天 10:42 已同步」「尚未同步」或「上次同步失败」，以便知道上一次同步的结果。
5. 作为桌面端用户，我希望未连接的设备显示「连接」按钮，点击后打开连接向导，连接成功后回到数据同步页且按钮变为「同步配置」，以便连接后选择同步内容。
6. 作为桌面端用户，我希望上次同步失败的设备显示「重试」，点击后打开该设备的同步弹窗，以便重新处理失败项。
7. 作为桌面端用户，我希望在没有任何远端设备时看到空状态和「连接远端设备」按钮，以便从这里开始添加连接。
8. 作为桌面端用户，我希望未安装的设备和所有连接配置都已退役的设备不出现在列表中，以便列表里只有可以同步的设备。

### 弹窗与概览

9. 作为用户，我希望同步弹窗沿用迁移向导的外观：左侧分类导航，右侧内容，底部固定操作栏，以便与已有的迁移体验一致。
10. 作为用户，我希望弹窗顶部显示目标设备的状态点、名称、传输方式和目标地址，以便确认推送目标。
11. 作为用户，我希望弹窗打开时先显示概览，以便先了解整体差异再逐类处理。
12. 作为用户，我希望概览每一行显示分类名、本机数量、远端数量和「N 项变更」或「已一致」，以便判断哪些分类需要处理。
13. 作为用户，我希望点击概览的某一行进入该分类详情，而点击行前的勾选框不跳转，以便选择和浏览互不干扰。
14. 作为用户，我希望概览的分类勾选框有全选、部分选、未选三种状态，并与分类页的勾选同步，以便批量控制「推送全部」的范围。
15. 作为用户，我希望点击「推送全部」时，只推送已勾选条目的分类，以便一次完成多类同步。
16. 作为用户，我希望推送全部期间按钮显示「全部同步中…」，完成后显示「已全部同步」，以便了解整体进度。
17. 作为用户，我希望分类数据加载期间，概览按行显示加载状态，而不是整个弹窗卡住，以便先看到已经算好的分类。
18. 作为窄窗口用户，我希望分类导航变成顶部可横向滚动的标签，以便小窗口下也能使用。

### 条目状态与选择

19. 作为用户，我希望只在本机存在的条目显示绿色「推送」，并且默认勾选，以便缺失项一键补齐。
20. 作为用户，我希望本机版本较新的条目显示「v5 → v6」和蓝色「更新」，并且默认勾选，以便把远端升级到本机版本。
21. 作为用户，我希望远端版本较新的条目显示「本机版本较旧」和黄色「差异」，并且默认不勾选，以便不会无意中降级远端。
22. 作为用户，我希望没有版本号且内容不同的条目显示「内容不同」和黄色「差异」，并且默认不勾选，以便由我决定是否覆盖。
23. 作为用户，我希望可以主动勾选黄色「差异」项，以便明确用本机内容覆盖远端。
24. 作为用户，我希望两端内容一致的条目显示灰色「已同步」，并且不可勾选，以便减少无效操作。
25. 作为用户，我希望列表按「推送 → 更新 → 差异 → 已同步」排序，以便先看到需要处理的项。
26. 作为用户，我希望远端独有的条目不出现在推送列表中，也永远不会被删除，以便远端自己的配置是安全的。
27. 作为用户，我希望不能同步的条目显示为不可选，并在说明行写明原因（例如超过大小上限、目标是软链、来源已删除），以便知道为什么不能推送。
28. 作为用户，我希望分类页底部显示「将同步 N 项」，未选任何项时显示「未选择任何内容」且按钮不可用，以便确认推送范围。
29. 作为用户，我希望分类页有「全选」和「取消选择」，以便快速调整选择。

### 推送执行

30. 作为用户，我希望点击「推送{分类}」后按钮显示「同步中…」，完成后显示「再次同步」，以便知道当前状态。
31. 作为用户，我希望推送完成后列表自动刷新，刚推送的条目变为「已同步」，以便确认结果。
32. 作为用户，我希望部分条目失败时，失败项在行内显示原因，底部汇总失败数量，其余成功项正常完成，以便只处理失败项。
33. 作为用户，我希望列表加载后远端如果又被修改，推送时不覆盖这次修改，而是提示「远端已变化，请刷新后重试」，以便不丢失远端的新修改。
34. 作为用户，我希望推送前先检查远端目录可写，无写权限时直接给出明确错误，以便不出现推送了一半的状态。
35. 作为用户，我希望同步弹窗可以最小化到窗口右下角，推送继续执行；离开设置页后仍可恢复同一弹窗，查看进度和结果。推送期间不能关闭或全局取消，以便推送结果不被中途丢弃。
36. 作为用户，我希望推送中设备断开连接时，当前分类标记为失败，弹窗显示设备离线并禁用操作，以便知道推送没有完成。
37. 作为用户，我希望新建到远端的条目带上本机的启用/禁用状态，而更新已有条目时保留远端的启用状态，以便远端的开关选择不被覆盖。
38. 作为用户，我希望推送后远端的技能、命令、MCP、插件列表立即生效，以便马上在远程会话中使用。

### 各分类

39. 作为用户，我希望技能同步包含 `~/.zcode/skills` 和兼容目录 `~/.agents/skills` 下的用户技能，并统一写入远端 `~/.zcode/skills`，以便两种来源都能同步。
40. 作为用户，我希望从技能商店安装的技能显示真实版本变化，以便判断是否需要更新。
41. 作为用户，我希望 MCP 服务器同步时自动把本机 home 路径改写成远端 home 路径，以便 filesystem 类 MCP 在远端可用。
42. 作为用户，我希望 MCP 配置里的环境变量和请求头按原样同步，以便远端 MCP 直接可用；我理解它们会写入远端配置文件。
43. 作为用户，我希望 marketplace 插件在远端按同一来源重新安装，Personal Source 的本地目录来源会先镜像到远端，以便远端得到同样的插件。
44. 作为用户，我希望 marketplace 插件在远端添加或安装期间可以按行「停止」，以便中止单个耗时过长的插件。
45. 作为用户，我希望只有远端来源的最新版本等于本机版本时，marketplace 插件才能「更新」，以便更新结果和看到的一致。
46. 作为用户，我希望 Builtin Plugin 不出现在列表中，以便不重复同步远端自带的插件。
47. 作为用户，我希望 Orphaned Installed Plugin（来源已删除）显示为不可同步并说明原因，以便理解为什么不能推送。
48. 作为用户，我希望子智能体按名称对齐、按原文件推送，以便模型、工具、技能等所有字段原样保留。
49. 作为用户，我希望子智能体引用的 MCP 或技能在远端不存在时，行内提示缺失项，以便我决定是否一并推送依赖。
50. 作为用户，我希望本机给内置子智能体（general-purpose、Explore）设置的模型也能推送到远端，并在内容不同时看到远端当前的模型，以便远端的内置子智能体使用同一个模型。
51. 作为用户，我希望命令同步包含 `~/.zcode/commands` 和兼容目录 `~/.agents/commands` 下的命令，并统一写入远端 `~/.zcode/commands`，以便两种来源都能同步。
52. 作为用户，我希望命令按相对路径（例如 `/git/commit`）对齐并按原文件推送，以便子目录结构保持不变。
53. 作为用户，我希望每条钩子定义作为一项单独同步，行内显示事件、matcher 和完整命令，以便清楚知道将在远端执行什么。
54. 作为用户，我希望推送钩子时只合并选中的定义，远端已有的其他钩子和其他配置保持不变，以便不破坏远端配置。
55. 作为用户，我希望模型提供商分类列出本机的提供商（API Key 掩码显示），并显示上次自动同步的时间和结果，以便确认远端的模型配置是最新的。
56. 作为用户，我希望自动同步失败时，模型提供商分类显示失败原因和「重试」按钮，以便自己修复，不用等下一次自动触发。
57. 作为用户，我希望设备上没有已打开的项目时，模型提供商分类提示「打开该设备上的项目后自动同步」，以便知道模型配置什么时候下发。
58. 作为用户，我希望模型提供商不参与勾选和「推送全部」，以便模型配置始终以本机为准整体下发。

### 入口统一

59. 作为用户，我希望连接向导、Header 更多菜单、侧栏远端项目菜单，以及技能、MCP、插件设置页里原来的同步入口，都打开同一个数据同步弹窗，并定位到对应的设备和分类，以便同一种同步只有一套界面和行为。
60. 作为用户，我希望从连接向导或项目菜单进入时，MCP 的 workspace 路径也按当前项目映射，以便项目路径相关的 MCP 在远端可用。
61. 作为 Docker 远端用户，我希望 Docker 远程项目也显示这些同步入口，以便与 SSH、WSL 远程项目一致。

64. 作为用户，我希望打开设置时默认选中当前 workspace 所在设备的「用户」，以便直接修改正在使用的那台设备。
65. 作为用户，我希望不打开远程项目也能编辑远端设备的用户级配置，以便直接维护远端 `~/.zcode`。
66. 作为用户，我希望离线设备不出现在 Scope 菜单中，以便不选中一个无法读写的目标。
67. 作为用户，我希望所有使用 Scope 菜单的配置设置页（插件、MCP、技能、子智能体、命令、钩子）遵循同一规则，以便不再出现各页归属不一致的情况。

### 迁移入口

74. 作为用户，我希望浅色和深色主题下所有状态标签都清晰可读，以便在两种主题下都能使用。

## Implementation Decisions

### 范围

- 只同步 User 级配置：本机 `~/.zcode` 推送到远端 `~/.zcode`。项目级配置已经在远端项目目录里，不参与同步。
- 只做推送（本机 → 远端）。拉取方向本期不做，但所有接口和弹窗状态都保留 `direction` 概念，两端服务保持对称，以后补拉取时不需要改服务形状。设计稿的「推送到远端 / 拉取到本机」分段控件本期隐藏。
- 会话和记忆分类本期隐藏，概览也不显示这两行。
- 设备范围：本机已知的 Source Server，传输方式为 SSH、WSL、Docker。设备的 `installState` 必须为已安装，且至少有一条未退役（`lifecycleState` 不是 `retired`）的 Connection Profile。dev-only 的 Server 直连不在列表中。
- 数据同步页只在桌面端显示。Web 与手机远控不显示。

### 服务归属与数据流

弹窗不新建 Host、连接或 Agent。本机一侧用 base services；远端一侧用该设备已有的 source-settings attachment，不需要打开 workspace tab。同步数据只在两端服务之间经 RPC 传输。比较逻辑是 Renderer 中的纯函数。

```text
DataSyncDialog（Renderer）
   source = 本机 base services
   target = 设备 source-settings attachment services
         │
         ├─ list(category) ─────────▶ 本机 Host ──▶ 条目 + 版本 + 轻量签名
         ├─ list(category) ─────────▶ 远端 Host ──▶ 条目 + 版本 + 轻量签名
         ├─ contentHashes(keys) ────▶ 两端并行（只针对两端都有且签名相同的项）
         ▼
   compare(source, target) ──▶ 行状态 + 默认勾选
         ▼  用户点击推送
   source.export(keys)
     → target.checkWriteAccess(category)
     → target.import(payload, 每项 mode, expectedTargetHash)
     → 每项结果：created / updated / skipped / conflict / failed
         ▼
   设备同步状态写入本机（lastSyncAt / lastResult）──▶ 设备列表读取
```

- 推送按分类串行执行，同一分类内由目标端一次导入。
- 任一分类同步期间，概览、各分类页与模型提供商页均显示当前正在同步的分类（如「正在同步插件…」）。进度从已有分类 `push` 状态派生；分类交接期间没有活动分类时显示通用「同步中…」。所有推送按钮按整批同步状态显示进行中文案和旋转图标；当前分类已失败或完成也不提前显示「再次同步」。整批结束后移除进度提示，失败项保留并可再次同步。仅展示改变，不增加第二份同步状态、不放开并发推送。
- 推送后刷新（刷新该设备上已打开项目的运行态）不属于推送本身。分类导入结束后，刷新进入弹窗内的刷新队列，按推送顺序逐个执行。分类结果、设备同步状态写入和下一次推送都不等待刷新。刷新失败只记录日志，不改变推送结果。原因：原来推送要等刷新结束；刷新一直不返回时，推送不能结束，设备同步状态不写入，之后的推送被静默忽略。
- `expectedTargetHash` 用于乐观并发：目标端导入前重新计算目标项的哈希，与列表时不一致则返回 `conflict`，不写入。
- 弹窗绑定某个设备的一次连接（generation）。该连接断开后，迟到的结果一律丢弃。设备离线时弹窗不自动关闭，而是显示离线状态并禁用操作；重新上线后重新加载列表。
- 弹窗右上角提供「最小化」，不取消推送。窗口级 `DataSyncDialogProvider` 持有当前弹窗请求及展开/最小化状态；设置页和旧入口只发打开命令，不持有推送实例。最小化后右下角状态条显示设备与同步状态，点击恢复；同步结束仍保留状态条，不自动抢回焦点。切换设置分类、关闭设置页或切换任务不卸载同步实例。当前弹窗未关闭时，再次打开同步入口恢复当前弹窗，不替换目标或重启推送。
- 推送进行中禁止关闭弹窗，Esc 和点击遮罩也不关闭；最小化是独立的展示状态，不改变 `useDataSyncDialog` 的 generation、push session、选择、分类和结果。断线仍按原有规则失败，状态条可恢复查看。该功能只在已有桌面同步入口提供，Web 与手机远控不新增同步入口。弹窗没有全局取消。marketplace 插件行在远端 add / install 期间显示「停止」，复用现有的 `cancelPluginOperation`；停止只作用于该行。
- 推送结束后的页面刷新只有一个来源：窗口级 Provider 写入设备同步状态后递增结果版本。数据同步页和技能、MCP、插件设置页订阅该版本，推送结束时已挂载的页面各重新读取一次；页面新挂载时自行加载，不重复刷新。刷新不绑定打开弹窗的入口。原因：原来设置页的刷新回调绑定在打开弹窗的页面实例上；最小化后该页卸载再挂载，或从数据同步页、状态条恢复弹窗时，推送结束只调用已失效的旧回调，设置页列表停在推送前。

```text
设置 / 旧入口 → 窗口级弹窗请求 → useDataSyncDialog（唯一推送 owner）
                    ├─ 展开 ↔ 最小化（只切换展示）
                    ├─ 页面切换：保留实例、分类、选择与在途请求
                    └─ 推送结束：记录设备结果 → 结果版本 +1
                                   └─ 当时已挂载的数据同步页 / 设置页各刷新一次
设备断线 → 原 generation 作废 → failed；恢复展示不重试、不发第二次推送
```

### 比较依据与性能

- 不存储哈希，不建同步基线，不使用 mtime。原因：导入会把 mtime 重置为同步时刻；两台机器时钟可能不同；git checkout 和编辑器也会改动 mtime。
- 一致性判断：每端在本机现场计算内容哈希。目录类按「相对路径 + 字节」递归计算；JSON 条目先排序 key 再计算，并排除启用状态字段。
- 版本来源：插件为 Plugin Manifest 版本，marketplace 插件取两端 overview 中的版本；技能只有商店安装的技能有版本（安装元数据）。MCP、子智能体、命令、钩子没有版本。
- 性能措施（本机实测：137 个技能、约 111MB，串行全量哈希约 0.4–0.8 秒，文件数 + 字节预检约 0.1 秒）：
  1. 只为两端都存在的项计算哈希。
  2. 先比较文件数和总字节数，不同就直接判为内容不同；相同时才计算全量哈希。
  3. 超过大小上限的项（技能 20MB、插件 50MB）直接标为不能同步，不计算哈希。
  4. 两端并行计算，概览按分类逐行显示加载状态。
  5. 弹窗打开期间缓存结果，推送后只重算受影响的项。
- 网络上只传哈希字符串和元数据，不传文件内容。
- 覆盖时的 `expectedTargetHash`：目标端对两端都有、且能同步的项都计算哈希，作为列表加载时的基线；来源端只在签名相同、版本不能决定结果时计算。超限、软链等不能同步的项两端都不计算。
- 弹窗内缓存按「key + 签名」复用哈希；推送涉及的目标项（含冲突、失败项）在推送后失效，重连后清空目标端缓存。
- 单个分类内按来源字节分批导出、导入（技能每批不超过 20MB），批次串行。父子技能同时勾选时放进同一批（见「技能」）。某一批导出或导入抛错时，只把该批各项记为失败（原因写在行内），其余批次照常推送；推送结束后按全部结果汇总，并照常刷新目标列表。写权限预检失败仍按整个分类失败处理。

### 统一的同步服务形状

每个分类在两端实现同一组能力。Renderer 通过一个按分类分派的适配层调用：

- `list(category)`：返回本端的 User 级条目。每项包括对齐 key、显示名、说明元数据、可选版本、轻量签名（文件数、总字节）、启用状态、能否同步及原因。JSON 类条目的哈希很便宜，可以直接返回。
- `contentHashes(category, keys)`：返回指定项的内容哈希。来源端调用时带上目标端 `list` 返回的 home 路径（`targetHomeDir`）；需要路径改写的分类（MCP）先按目标端路径改写再计算，其他分类忽略该参数。
- `checkWriteAccess(category)`：沿用现有写权限预检（写入并删除一个标记文件），超时 15 秒。
- `export(category, keys)`：目录类返回归档字节，JSON 类返回条目数据，同时带上来源 home 路径。
- `import(category, payload, items)`：`items` 为每个 key 指定 `createOnly` 或 `overwrite`，以及 `expectedTargetHash`；返回每项结果。

落地方式：

- 技能、MCP、插件沿用现有三个服务通道，扩展为上述形状。原有的「列出远端状态」类方法被目标端 `list` 取代，旧弹窗删除后一并删除。
- `list` 结果可以带分类级的 `importBlockedReason`：该端作为目标时整类不能导入，比较时所有行都标为不能同步，两端都不计算哈希（MCP 远端使用 `~/.agents` 兼容配置时）。
- 方法名统一为 `listSyncItems`、`getSyncContentHashes`、`checkSyncWriteAccess`、`exportSyncItems`、`importSyncItems`，接口 `IDataSyncCategoryService<TPayload>`（`packages/services/src/data-sync/contract.ts`）。共享类型在 `packages/shared/src/remote-sync.ts`。
- 写权限预检的 15 秒超时在 Renderer 实现；技能分类同时预检 `~/.zcode/skills` 与 `~/.zcode/cli`（新建禁用项要写 `config.json`）。
- 子智能体、命令、钩子新增一个服务通道，按 category 区分，在两端注册。新通道加入远程 workspace RPC 合同、source-settings 服务集合和远端 bundle 部署检查标记。R3 兼容门要求两端同版本，所以不需要做能力协商。
  - 通道 `user-config-sync`，接口 `IUserConfigSyncService`（accessor `userConfigSyncService`）。方法与 `IDataSyncCategoryService` 相同，每个方法多一个 `category` 参数（`UserConfigSyncCategory`），未知 category 直接报错。Renderer 适配层按 category 把它绑定成单个分类服务。
- marketplace 插件依赖 Agent 的 add / install / update RPC，不放进文件型服务，保留独立的编排逻辑；编排逻辑同样以 source / target 为参数，不写死方向。
- MCP 导入的路径参数改名为 `sourceHomeDir`、`sourceWorkspacePath`、`targetWorkspacePath`，避免方向歧义。
- workspace 映射：`getSyncContentHashes` 与 `exportSyncItems` 有可选参数 `workspace`（`DataSyncWorkspaceMapping`：`sourceWorkspacePath` 本机项目路径、`targetWorkspacePath` 远端项目路径）。弹窗只把它传给来源端；MCP 计算来源哈希时先做 workspace 改写再做 home 改写，导出时把它写进 payload，目标端导入时据此改写。其他分类忽略该参数。弹窗不带映射打开时只做 home 改写。

### 覆盖（更新）的通用规则

- 目录类条目（技能、inline 插件）：解压到目标端同一磁盘的临时目录 → 原目录改名为备份 → 新目录改名到位 → 成功后删除备份，失败则还原。
- 文件类条目（子智能体、命令）：原样复制文件字节，原子替换。不经过现有的表单保存接口，因为它会重新生成文件并丢掉未知字段。
- JSON 类条目（MCP、钩子）：写前重新读取目标文件，只修改选中的条目，其他字段原样保留，原子写入。
- 启用状态：新建时带上来源的启用状态，以绝对路径为键的配置要换算成目标端路径；更新时保留目标端的启用状态。
- 以下目标不覆盖，标为不能同步：
  - 目标是软链；
  - 目标位于 `~/.agents` 兼容目录；
  - inline 插件的目标目录不在远端 `~/.zcode/plugins` 下。
- 目录类条目（技能、inline 插件）的目标目录之内还有目标端的其他条目时也不覆盖，例如嵌套技能 `parent/child`，或登记在另一个 inline 插件目录之内的插件。整目录替换会删除这些独立条目，或用来源版本改写它们。列表阶段不预先标出；导入时先做这项检查，再做内容哈希检查，该项失败，原因写明被包含的条目路径。

### 各分类规则

**技能**

- 来源：`~/.zcode/skills` 与 `~/.agents/skills`，按现有规则去重，结果统一写入远端 `~/.zcode/skills`。
- 对齐 key：归一化的 skill name（去空白、转小写）。目录名只表示位置；同名不同目录时以目标端实际路径为准。
- SKILL.md 没有 frontmatter name 时，name 取技能目录的最后一段（例如 `group/plain` 取 `plain`）。两端扫描和目标端导入用同一规则；导入时校验 name 与 key 一致，不一致该项失败。
- 技能目录内部含软链时不能同步（现有限制）。
- 启用状态：新建项按来源状态写入目标端 `config.json` 的 `skills`（键为目标端 SKILL.md 路径）。来源禁用时写 `{ enable: false }`；来源启用、但目标端同一路径残留禁用项时删除该键（开启态不落盘）；来源启用且没有残留时不写 `config.json`。写入失败时只回滚需要写状态的新建项（删除目录，该项失败）。
- 嵌套技能（技能目录之内还有其他技能，例如 `parent` 与 `parent/child`）：
  - 只选父技能时，子技能的文件随父目录一起写入（现有行为）。
  - 父子同时勾选时，子技能跟随父技能一起写入。`list` 为技能给出 `parentKey`（同一端内目录包含它的最近一个技能）。弹窗推送时沿 `parentKey` 链找到最上层的已选上级（链上未勾选的中间项也穿过），同组放进同一批，上级在前；该组按最上层上级的字节计入批次（父目录字节已包含子目录）。
  - 导出：选中项的目录位于另一个选中项的目录之内时不单独打包；payload 仍列出全部选中项。
  - 导入（服务是边界，不依赖弹窗顺序）：按来源目录层级先上级后下级处理。下级位于本次已写入（新建或更新）的上级之内时，文件已随上级写入，位置是上级的目标端路径加相对路径：目标端原来没有该技能则为「新建」，之后照常写启用状态；目标端原来在其他目录已有该技能则该项失败，原因写明已随上级写入、目标端另一处已有同名技能、未覆盖它。上级没有写入（失败或冲突）时，下级按普通规则独立导入。
  - 覆盖父技能时，目标端父目录之内有其他技能仍然失败（见「覆盖（更新）的通用规则」）。
- 推送后刷新远端技能列表，并使草稿会话失效（沿用现有刷新逻辑）。

**MCP 服务器**

- 来源：本机「有效用户 MCP」（`~/.zcode/cli/config.json` 的 `mcp.servers`；为空时回退 `~/.agents/mcp.json`）。
- 对齐 key：server name，比较时转小写，写入时保留原大小写：新建按来源名称写入；覆盖沿用目标端已有的名称，只替换该 server 的配置。
- 比较前先把来源配置改写成目标端路径，再比较排除启用状态后的规范化 JSON（key 排序，排除 `enabled` 和历史遗留的 `enable`）。MCP 条目没有签名，不进弹窗内哈希缓存，每次加载都重新计算。
- 路径改写：不论从哪个入口打开，都做 home 改写。home 改写的范围保持现状：只改写 filesystem 类 stdio MCP 的 `args`，不改写其他 MCP 的 args、env、cwd。从带 workspace 上下文的入口（连接向导、Header、侧栏项目菜单）打开时，再做 workspace 改写。从设置页打开时只做 home 改写，MCP 设置页入口也不做 workspace 改写。
- env、headers 原样写入远端配置文件，文件权限 0600。MCP OAuth token 不同步，远端需要重新授权。
- 如果远端的有效 MCP 来自 `~/.agents/mcp.json`（即远端 `.zcode` 中没有任何 server），本分类整体不能推送，原因写「远端使用 ~/.agents 兼容配置，推送会使其失效」。

**插件**

- 只处理 scope 为 user 的插件。Builtin Plugin 不列出。
- inline 插件：
  - 来源为 `~/.zcode/cli/config.json` 中 `plugins.dirs` 登记的目录（服务 `pluginSyncService`，方法见「统一的同步服务形状」）。
  - 对齐 key 为 `name@inline`（转小写，name 取 Plugin Manifest）；目录名只表示位置。比较 Plugin Manifest 版本与目录内容哈希。同 id 重复登记时取第一项，与 CLI 运行时一致。
  - 导出时排除插件目录顶层的 `data/`，签名和哈希也不计入；覆盖时保留目标端的 `data/`、启用状态和 options。CLI 运行数据目录 `~/.zcode/cli/plugins/data/<id>` 不在插件目录中，同步不触碰。
  - 单项上限 50MB，按目录原始字节（不含 `data/`）计算；每批导出、导入不超过 50MB。写权限预检 `~/.zcode/plugins` 与 `~/.zcode/cli`。
  - 新建：写入远端 `~/.zcode/plugins/<来源目录名>`，目录名被占用时加短哈希后缀；再一次写入 `config.json` 的 `plugins.dirs`、启用状态（`plugins.enabledPlugins`）和 options（`plugins.options`）。写 `config.json` 失败时删除本次写入的目录，该项失败。
  - 更新：原目录改名为同盘备份，备份中的 `data/` 移入新目录后换上；失败时还原。`config.json` 不改。
  - 远端 `plugins.dirs` 中的同名插件不在远端 `~/.zcode/plugins` 下（例如开发中的 checkout）时不能更新，原因写「远端同名插件位于 ~/.zcode/plugins 以外的目录（例如开发中的 checkout），不能更新」。
  - 新建时只同步安全子集的 options：已配置、非敏感、非路径类（`file` / `directory`）、类型与远端 schema 匹配的值。来源端导出前按本机 manifest 的 `userConfig` 筛一次（敏感值不离开本机），目标端写入前按刚写入的 manifest 再筛一次，与远端已有的同 id options 合并。
  - 推送后对该设备上已打开的项目复用插件刷新链：技能、slash commands、MCP，再发插件管理通知。
- marketplace 插件：
  - 数据来源：每端各自调用插件管理服务（`pluginManagementService`，两端都在 source-settings 服务集合中）的 `getPluginsOverview` / `listPlugins`，参数 `configScope: "user"`、`workspacePath` 为该端 Host 的 home（`systemService.info().homedir`），不带 workspace identity。与设置页远端 User scope（source home 作为 workspacePath）口径一致，从设置页打开时不需要项目。
  - 候选：overview `installedPlugins` 中 scope 为 user 的插件；`listPlugins` 中 source 为 `official` 的插件（Builtin Plugin 和官方资源包自带的插件）不列出。
  - 对齐 key 为 `name@marketplace`（转小写，`pluginId` 保留大小写）；只比较两端 overview 中的版本，不计算哈希。版本字符串相同即「已同步」。
  - 新建：沿用现有流程。目标端 catalog 中没有该插件时先准备来源：网络来源（github / git / url）在远端 add；Personal Source 的本地目录类来源（file / directory / settings）先把 marketplace 清单和本机已安装的该 marketplace 插件源码镜像到远端，再用镜像路径 add；官方 marketplace 两端默认存在，不 add。然后在远端安装（`installPlugin`，scope user）、设置启用状态、同步安全 options（规则与 inline 插件相同，与远端已有的同 id options 合并后 configure）。
  - 更新：只有远端来源的最新版本（远端 catalog 中该插件的版本）正好等于本机版本时才可勾选，否则不能同步，原因写「远端来源的最新版本与本机不一致」。更新用 `installPlugin` 从远端 catalog 重新安装（与 Agent 的 update 同一实现，且支持取消），保留远端的启用状态和 options；完成后先恢复远端原来的启用状态，再核对远端版本，与本机不一致时该项失败（失败时启用状态同样保持原值，不因重新安装被默认启用）。
  - 远端较新时显示黄色「差异」且不可勾选，因为 RPC 不支持指定版本或降级。
  - Orphaned Installed Plugin（本机来源已删除，overview 中没有该 marketplace）不能同步，原因写「来源已删除」。
  - 本地目录类来源镜像不支持跨 marketplace 的依赖：列表时由来源端 `pluginSyncService.inspectMarketplaceSourceMirror` 检查依赖闭包，有跨 marketplace 依赖的插件不能同步并写明原因。其他来源类型（如 npm）不能同步，原因写「来源类型不支持同步」。
  - 远端 add / install 期间，该行显示「停止」，复用 `cancelPluginOperation`。停止只作用于该行：该项立即结束并记为失败（显示「已停止」），其余项继续；远端已经开始的操作可能仍会完成。
  - 写权限预检与 inline 插件相同（`~/.zcode/plugins` 与 `~/.zcode/cli`）；每项单独成功或失败。
- 插件埋点：每个插件（inline 与 marketplace）在目标端导入结束后上报一条 `plugin_lifecycle`（action 与 trigger 均为 `sync`），结果按目标端导入结果映射为 success / failure / cancelled（「已停止」）/ noop，带耗时；inline 插件按批导入，耗时为该批的耗时。合同见 [插件生命周期业务埋点](../monitoring/plugin-lifecycle-telemetry.md)。

**子智能体**

- 来源和目标各自按本端的存储根目录解析，两端的存储目录配置可能不同。
- 对齐 key：name 转小写。按原文件字节同步；哈希在本端完成 markdown 迁移之后计算。
- 只读用户 agents 根目录下一层的 `.md` / `.markdown` 文件（与运行时发现范围一致）；同一端有多个文件解析出同一个 key 时，取路径排序中的第一个。单个文件的哈希很便宜，`list` 直接返回 `contentHash`。
- 新建时沿用来源的文件名写入目标根目录；该路径已被占用（例如另一个 name 的文件）时该项失败。更新时同目录临时文件 + rename，替换目标端该 name 对应的实际文件，保留其文件名和权限位。
- 禁用状态存在 `<存储根>/v2/agents-state.json` 的 `disabledAgentIds`，键为 `user:user:<name 小写>`，不需要路径换算。新建项只在来源状态与目标端当前状态不一致时才写状态文件：来源禁用时加入该 ID，来源启用而目标端残留该 ID（例如以前删除的子智能体留下的）时删除该 ID。写入失败（例如状态文件损坏）时，删除本次新建的文件并标为失败。状态文件损坏时按全部启用读取，所以来源启用的新建项不写状态文件，照常新建。
- 禁用状态按启用状态通用规则处理。
- 内置智能体的模型覆盖（2026-11-02 增加，票 [20](../issues/data-sync/20-builtin-subagent-model-overrides.md)）：存在同一状态文件的 `builtInModelSelectionOverrides`，在本分类中和用户子智能体放在同一个列表里，不分组。插件智能体的模型覆盖（`pluginAgentModelSelectionOverrides`）属于本机状态，不同步。
  - 每个有覆盖的内置智能体算一项。没有覆盖（继承默认）的内置智能体不是条目，所以本机继承默认时不列出该行，远端的覆盖保持不变（推送永不删除远端独有的条目）。远端要恢复继承默认，在设置页的 Scope 菜单中选中该设备后修改。
  - 对齐 key 是内置智能体的状态 ID（`built-in:built-in:<name 小写>`，与 `createAgentStateId` 相同），显示名为 `general-purpose` / `Explore`。key 带前缀，不会与用户子智能体的 key 相同。
  - 内容哈希按规范化后的 Model Selection（`providerId`、`modelId`、推理档位）计算，`list` 直接返回。读取时每项单独校验，与设置页、运行时的读取规则相同；状态文件缺失或损坏时按没有覆盖处理。
  - 行状态沿用通用规则：只在本机有覆盖为「推送」，两端相同为「已同步」，两端不同为「差异 · 内容不同」。
  - 说明行显示「内置 · 模型 `<modelId>` · 推理档位 `<档位>`」，没有档位时省略后半段。「差异」行在说明下方再显示远端当前的模型：「远端：`<modelId>` · 推理档位 `<档位>`」。只显示 `modelId`：远端 source-settings 没有模型目录，拿不到模型显示名和 Provider 名称。
  - 导入：先迁移并重新读取目标端状态文件，再逐项核对。`createOnly` 时目标端已有覆盖、`overwrite` 时目标项哈希与 `expectedTargetHash` 不一致，都返回 `conflict`。只写 `builtInModelSelectionOverrides` 中通过核对的项，其他字段原样保留，原子写入。没有项通过核对（例如全部冲突）时不写文件。状态文件损坏时这些项失败，不写入。
  - 不校验远端是否有对应的 Provider、模型和推理档位，与用户子智能体 frontmatter 中的 `model` 相同。远端没有时，调用该内置智能体报 `provider-not-found` 或 `reasoning-level-missing`，不回退到父会话模型。Provider 本身由 Provisioning 下发。
  - 生效时机与用户子智能体相同：远端 Host 监听状态文件，下一个父轮生效，推送前已有的 task 也一样。
- 推送后，以及在设置页改动远端「用户」的子智能体后，刷新该设备上已打开项目斜杠（/）建议中的子智能体：按每个项目已注册的服务逐个刷新。取不到服务的项目跳过，不回退到本机。原因：建议缓存按项目的服务对象分桶，推送和远端「用户」使用的 source-settings 服务刷新不到这些缓存。
- 依赖提示：子智能体引用的 MCP 或技能在本机对应分类列表中存在、且在目标端列表中不存在时，行内说明「远端缺少 MCP：x」或「远端缺少技能：y」。只提示，不阻止推送。依赖信息来自同一弹窗中 MCP 和技能分类的两端列表。
  - 内置技能、插件提供的技能 / MCP 不在用户级列表中，不提示（本弹窗也无法推送它们）。
  - 依赖取自 frontmatter 的 `mcpServers` 与 `skills`，只认运行时支持的字符串名称；`mcpServers` 的对象形式是内联配置，不作为依赖。子智能体 `list` 项带 `dependencies`。
  - 按两个分类的对齐规则匹配（名称 trim 后转小写），不新增 RPC。某分类的本机或目标端列表加载中或加载失败时，不判断该类依赖。
  - 多个缺失项合并为一行，例如「远端缺少 MCP：a、b；远端缺少技能：c」，用 `warning-surface-foreground` 文字色显示在说明下方。行状态和默认勾选不变。
  - MCP 或技能推送后该分类重新加载，提示按最新的目标端列表重新计算，依赖已推送时自动消失。

**命令**

- 来源：`~/.zcode/commands` 与 `~/.agents/commands` 合并，递归扫描。合并规则与 CLI 运行时一致：两个目录有同名命令时，`.zcode` 优先。
- 目标：结果统一写入远端 `~/.zcode/commands`。目标端的列表也按同一规则合并两个目录。
- 对齐 key：去掉 `.md` 的相对路径，例如 `/git/commit`。key 转小写（CLI 运行时按小写命令名去重），显示名保留大小写。按原文件字节同步。
- 扫描跳过 `.` 开头的条目，不进入软链目录；单个文件的哈希很便宜，`list` 直接返回 `contentHash`。
- 新建时按来源相对路径写入目标 `~/.zcode/commands`，子目录结构保持不变；该路径已被占用时该项失败。更新时同目录临时文件 + rename，替换目标端该 key 对应的实际文件，保留其文件名和权限位。
- 远端同名命令位于 `~/.agents/commands` 时，按覆盖的通用规则标为不能同步（`compat-directory`）；远端同名命令是软链时同样不能同步（`target-symlink`）。只影响该项，本分类不整体禁用。
- 启用覆盖的键是绝对文件路径（`config.json` 的 `command`），新建时换算成目标端路径并带上来源状态；写入失败（例如 `config.json` 损坏）时删除本次新建的文件并标为失败。更新时保留目标端状态。
- 推送后对该设备上已打开的项目刷新 slash commands（沿用插件同步后的命令刷新）。

**钩子**

- 只同步 `~/.zcode/cli/config.json` 中的 `hooks`。`~/.agents/settings.json`、`~/.claude/settings.json` 中的只读来源不列出。
- 每条钩子定义算一项。对齐 key 是「事件 + matcher + 类型 + 命令」，process 类型再加 args，command 类型再加 shell。改了命令就算新的一项。
- 其余字段（超时、async、状态文案、透传字段）参与内容哈希，不同就显示「差异 · 内容不同」。
- 每条定义的 `enabled` 按启用状态通用规则处理：不参与内容哈希，只差 `enabled` 的两条定义显示「已同步」；新建时带上来源的 `enabled`，覆盖时其余字段替换为来源，保留目标端的 `enabled`。
- 写入时只合并到 `events[事件]` 中 matcher 相同的分组（目标端没有该分组时新建），其他钩子和其他配置原样保留。写前严格读取并重新读取 `config.json`，原子替换；文件损坏或 `hooks` 结构不合法时整批失败，不写入。不经过设置页的保存接口（它会整体重建 `events`）。
- 对齐 key 在服务端是上述字段的规范化哈希；`list` 直接返回内容哈希，不带签名。
- 不同步工作区信任记录。
- 推送后使该设备上已打开项目的预热会话失效（与设置页保存钩子相同）：会话只在创建时读取钩子，推送前打开的新建任务页要重建预热会话才能用上推送的钩子。钩子设置页每次进入都会重新加载，不需要另外刷新。
- 根级 `enabled`：只在来源开启时把目标打开，永远不把目标从开启改为关闭。
- 行内说明显示完整命令。设计稿不显示警告框，本规格保持不显示。

**模型提供商（只读）**

- 遵守 R3 §8.2 的「路线 A」：本机是 Provider 配置唯一的编辑方，Provisioning 自动整包下发。本分类不提供勾选，不参与「推送全部」。
- 列表显示本机 Personal Layer 中的提供商：名称、端点、模型。数据同步页不显示 API Key 明文：前端用掩码显示，不新增 Host 侧的掩码视图。
- Provisioning 只在设备有 lane 时执行。lane 在本机打开该设备上的项目时注册；本功能不新增无项目的下发链路。
- 设备有 lane 时，分类顶部的说明显示最近一次 Provisioning 的时间和结果。结果来自 Main 的 Provisioning 协调器，它按 lane 在内存中保留最近一次结果，并按 sourceServerId 提供给本机 Host；不新增持久化。
- 设备没有 lane 时，分类顶部显示「打开该设备上的项目后自动同步」，不显示结果，也不提供重试。
- 设备有 lane 且最近一次失败时，显示失败原因和「重试」按钮。重试复用协调器现有的 single-flight lane 和尾随同步，不新增第二条同步链路。这是 R3「模型配置没有用户触发的同步入口」的唯一例外：只在失败时出现。
- 说明文案改为「模型配置以本机为准，保存后自动同步到远端；API Key 和登录态随配置同步」。设计稿中「不同步 OAuth Token」的写法与现状不符：远端无法自己完成浏览器登录，依赖下发的登录态。
- 概览中本行的勾选框不可用。最近一次失败时，「差异」列显示「同步失败」；其他情况显示「自动同步」。本行的本机数量为列出的提供商数，远端数量显示「–」。
- 实现：本机 Host 服务 `IProviderProvisioningStatusService`（通道 `provider-provisioning-status`）提供 `getStatus({ sourceServerId, waitForIdle? })` 与 `retry({ sourceServerId })`，经 Host → Main 的 `provider-provisioning-lane-request` / `-result` 消息读写协调器（R3 §8.3.6）。它与设备同步状态一样只在桌面本机 Host 注册，不进入远程 workspace RPC 合同、source-settings 服务集合和手机白名单。返回 `{ lane: "none" }` 或 `{ lane: "present", running, lastResult?: { at, outcome, errorCode? } }`。
- 打开时读取一次；正在执行时再以 `waitForIdle` 等这次执行结束；重试等本次推进的代际执行完后返回结果。重试合并进正在执行的首次上线同步时，首次失败照常立即结束首次同步（发布屏障不等重试），重试随后在同一条 lane 上再执行一次，返回这次的结果。失败原因按固定阶段码显示本地化文案。

### 设备列表与设备同步状态

- 首页采用「清晰列表」布局：标题右侧是低强调的「迁移数据」入口，下一行说明为「同步本机配置到远端。」。说明后的信息按钮可通过点击、键盘打开「同步规则」浮层，内容为「仅新增或更新，保留远端独有内容。」。
- 设备行保留原有顺序，分为设备名称与地址、连接状态与同步记录、操作三栏。窄窗口将名称和地址放在第一行，状态与操作放在第二行。地址允许换行，状态不再拼接在地址末尾。
- 连接状态与同步结果分别展示：在线设备始终显示绿色「已连接」，下方显示已有的同步时间、尚未同步或红色「上次同步失败」。连接状态不能用来表示配置已同步。
- 「连接」使用 outline 按钮和插头图标；「同步配置」使用 primary 按钮和上传图标。连接中使用禁用的 outline 按钮和旋转加载图标；同步失败保留「重试」outline 按钮，使用重试图标。
- 设备来源：本机 Source Server 管理快照，包括设备记录、Connection Profile 和连接状态。不新增设备事实源。
- 过滤：只显示 `installState` 为已安装、且至少有一条未退役 Connection Profile 的设备。dev-only 的 Server 直连不显示。
- 传输方式和目标地址取自 Connection Profile。一台设备有多条 Profile 时，沿用 `getRemoteDevicePresentationInput` 的选择规则。
- 状态映射：

```text
                                                     设备同步状态服务 → 同步记录
```

- 「连接」打开已有的连接向导，执行设备级连接，不打开任何项目。安装、升级、身份确认和凭据输入都由连接向导处理。
- 连接向导的 `returnTarget` 新增 `data-sync`。从数据同步页打开时传入它，连接成功后回到数据同步页。
  - 「连接」按 `getRemoteDevicePresentationInput` 选出的 Profile 以设备管理模式打开向导（`completion: "device-management"`、`preferredProfileId`）。成功后 Root 回到发起时的设置 tab，不跳「远程设备」页；返回目标只在数据同步页仍挂载时有效，页面卸载后迟到或取消的结果被丢弃，不改变页面。
- 设备行的连接状态只取自管理快照。页面不另存连接状态。
- 设备同步状态：本机 Host 新增一个很小的状态文件，按 sourceServerId 记录 `lastSyncAt` 和 `lastResult`（`success` / `partial` / `failed`）。每次推送（单个分类或推送全部）结束后写入，作为设备行状态的唯一数据源。不写入 `setting.json`，不修改 Source 设备记录的 schema，也不同步到远端。
- 状态文件为 `<appConfigDir>/data-sync-state.json`（默认 `~/.zcode/v2/data-sync-state.json`），服务 `IDeviceSyncStateService`（通道 `device-sync-state`）只在桌面本机 Host 注册，不进入远程 workspace RPC 合同、source-settings 服务集合和手机白名单。
- 推送全部结束后只写一次；结果按条目汇总：没有失败为 `success`，全部失败为 `failed`，其余为 `partial`。推送中设备断开按失败写入。
- 空状态的「连接远端设备」按钮打开已有的连接向导，以设备管理模式完成连接，`returnTarget` 同样为 `data-sync`。

- 适用于所有使用共享 Scope 菜单的配置设置页：插件、MCP、技能、子智能体、命令、钩子。子智能体页 User 固定写本机的特殊规则随之取消。

  - 在线判断与数据同步页一致，只取自管理快照。设备离线时，即使旧的 attachment 仍在注册表中也不使用；页面只显示离线提示，不显示旧列表。attachment 或 home 目录未就绪时显示「正在连接」。
  - 远端「用户」以该设备的 home（`systemService.info().homedir`）作为接口锚点路径；本机「用户」沿用一个本机项目作锚点，没有本机项目时用本机 home。迟到的 home 结果只属于发起请求的那一代 attachment。
  - Scope 选中的目标是一组绑定：设备 authority、锚点路径、workspace identity 和该目标的服务。MCP、命令等单例 store 的读取、在途请求键、迟到判定和写入都只用这一组，不从当前 tab 推断路径、identity 或服务。同 home 的两台远端「用户」靠 authority 区分。本机目标（本机「用户」和本机项目）的 MCP 仍走本机平台路径，保留旧 common MCP 迁移；远端目标没有绑定服务时不读写，不回退本机。
  - 编辑表单内的 Scope 菜单只列出所在页面当前设备的「用户」和「项目」子菜单，结构与页面级菜单相同，不能在表单里换设备。

  - 用户选中的项目关闭或断开后，回退到同一设备的「用户」并提示；该设备离线时按 fail-closed 处理。
  - 插件商店入口（「浏览」「添加」）作用于当前 workspace 的 Host，所以只在选中当前 workspace 所在设备的「用户」时显示。
  - Web 与手机不能申请 source-settings attachment：远端设备只列出项目，没有「用户」；远程 tab 下默认选中当前远程项目。

### 写入安全加固

- 写 `~/.zcode/cli/config.json` 的写入方统一复用 `updateJsonObjectFile`：文件损坏时报错，不写入；写前重新读取，只改自己的字段，原子替换。原因：读失败当作空对象再写回，会冲掉整个文件。
- 写入方包括：
  - 命令、钩子、技能的设置服务；
  - 迁移导入（`packages/services/src/settings-sync/settingsSyncService.ts`，写入 MCP 和 `plugins.dirs`）。
    文件损坏时该项导入失败，迁移结果沿用现有的失败显示。插件目录已经放入时随之删除，修好配置后可以重试。
  - 主进程 MCP 设置页（`packages/desktop/src/main/mcpUserDirectory/index.ts`：新增 / 修改 / 删除、启用开关、历史覆盖清理、历史 `enable` 迁移）。文件损坏或根节点不是对象时拒绝写入，字节不变；写入权限 0600。启用开关和历史覆盖清理在没有对应 server 或覆盖项时不写文件。
  - MCP 数据同步导入（`packages/services/src/data-sync/mcpDataSync.ts`）。文件损坏时本批所有项标为失败。
- 不新增跨进程锁。`config.json` 的多个写入方各自做到「写前重读 + 只改自己的字段 + 原子替换」。
- 已知限制：这只能防止半截文件和「损坏当空对象」，不能防止并发写入互相覆盖。读取与替换之间没有锁，两个写入方同时执行时，后替换的一方会覆盖前一方刚写入的字段（例如技能开关或 MCP 配置丢失）。同一进程内的并发调用同样如此。写入方分布在桌面主进程（MCP 设置页）、Host（命令、钩子、技能、迁移导入、数据同步导入）和 CLI 自身（`apps/zcode-cli/packages/adapters/src/config/file-config.adapter.ts`），所以只在 `updateJsonObjectFile` 内加锁也不能覆盖全部写入方。根治需要 App 与 CLI 共用一套 `config.json` 锁协议，另建 issue。每次写入的窗口只有毫秒级，需要两个写入方几乎同时执行才会触发。这个竞态在本功能之前就存在，本功能新增的数据同步导入写入方使触发机会略有增加。

### 手机与 Web 边界

## Testing Decisions

好的测试只验证外部行为：目标端最终写入了什么、哪些内容被保留、用户看到了什么、能点什么。不断言内部函数调用顺序或私有状态。

### Seam ①：服务对（主要 seam）

- 同一个同步服务创建两个实例，分别指向两个临时 HOME，代表「本机」和「远端」。走完整的 list → contentHashes → export → checkWriteAccess → import，断言目标 HOME 上的文件和配置。不经过 RPC。
- 覆盖内容：
  - 各分类的对齐 key 与五种比较结果；
  - 版本比较；
  - 轻量签名预检；
  - 超限、软链、兼容目录、外部目录的不能同步判断；
  - 目录类覆盖的目标目录内嵌套了目标端其他条目时该项失败，嵌套条目保持原样；
  - 父子技能同推：两种导入顺序都写入两项；子技能在目标端另一处已存在时该项失败且不覆盖；上级没有写入时下级独立导入；`parentKey` 取最近的上级技能；
  - 嵌套且没有 frontmatter name 的技能按目录最后一段对齐；
  - createOnly 与 overwrite；
  - 原子替换和失败还原；
  - `expectedTargetHash` 冲突；
  - 启用状态通用规则；
  - MCP 路径改写，以及 POSIX / Windows 两种目标路径；
  - MCP home 改写只作用于 filesystem 类 stdio MCP 的 `args`；
  - 钩子按字段合并，根级 `enabled` 只开不关；
  - 命令和子智能体原样保留文件字节；
  - 命令来源合并 `.zcode` 与 `.agents` 两个目录，同名时 `.zcode` 优先；远端同名项位于 `.agents` 时不能同步；
  - `config.json` 损坏时拒绝写入。
- 先例：现有技能、MCP、插件同步服务的单测（临时目录 + 真实文件系统）。

### Seam ③：桌面 E2E

- 目标：在开发者自己的机器上，用真实的 Linux 远端包和真实的 Linux 容器验证数据同步。不依赖专用 Linux 服务器、VPN 或真实账号；只有「远端会话能否使用推送内容」一组用例需要模型回放（见下文覆盖内容最后一项）。开发机可以是 macOS 或 Linux；当前主要开发机是 Apple Silicon Mac，Docker 容器为 linux/arm64。
- 运行步骤：
  1. **打 Linux 远端包**：`ZCODE_ENV=test pnpm prepare:remote-assets:linux`，只构建 `linux-x64` 和 `linux-arm64`，写入当前版本的 mock-cdn 发布目录。必须用 `test`，与 E2E 桌面端的 `ZCODE_ENV=test` 一致：`ZCODE_ENV` 在构建时编译进远端 server，两端不一致时会连不同的后端域，远端的 E2E 测试钩子也会被关闭。
  2. **新建 Linux 容器模拟远程机器**：复用现有远程 harness 的 SSH 目标镜像（sshd + `dev` 用户），端口只绑定 `127.0.0.1`，每次运行新建，并设置随机密码。
  3. **E2E 在容器上做实际验证**：Electron 在开发机本地原生运行，通过 `ZCODE_E2E_SSH_*` 环境变量合同经 SSH 连接容器；首次连接时把对应架构的 Linux 包安装进容器，在真实的远端 zcode-server 上执行推送；远端断言用 docker exec 读取容器内的 `~/.zcode`。
- 本机 E2E 只需要 Linux 包，不触发全平台的远程资源构建，也不能误用开发时打的 production 包。

```text
开发机（本机）
 ├─ ① ZCODE_ENV=test pnpm prepare:remote-assets:linux ──▶ mock-cdn/releases/<版本>/（linux-x64、linux-arm64）
 ├─ ② docker：新建 Linux 容器（sshd + dev 用户，127.0.0.1:<端口>）
 └─ ③ wdio + Electron（ZCODE_ENV=test）
        ├─ SSH ──▶ 容器：安装 Linux 包 → 启动远端 zcode-server → 数据同步推送
        └─ 断言 ── docker exec ──▶ 容器内 /home/dev/.zcode
```

- 覆盖内容：
  - 设置 → 数据同步 → 设备 → 推送技能、MCP、插件、子智能体、命令、钩子，在容器内 `~/.zcode` 断言实际写入的内容；
  - 远端已有的不同内容默认不被覆盖，手动勾选后才覆盖；
  - 父子技能同时推送到空远端，两个技能都写入；
  - 6 处旧入口打开的是新弹窗，并定位到正确的设备和分类；
  - 离线设备的「连接」流程：由 runner 让设备离线再恢复，在连接向导中完成连接后回到数据同步页；
  - 模型提供商下发失败后重试：先打开该设备上的项目，再用 docker exec 让容器内目标目录只读，制造失败；
  - Scope 菜单选中远端设备的「用户」后，编辑写入远端；
  - 远端「用户」的子智能体编辑表单打开时设备离线，再切到「本机 · 用户」：不显示旧表单，本机不写入；
  - 推送子智能体后，在已打开的远程项目输入 / 能看到新子智能体；
  - 「迁移数据」按钮直接进入向导第一步；
  - 没有打开项目时从「迁移数据」导入用户级技能，完成页显示已导入，文件写入本机 `~/.zcode/skills`。
  - 推送后远端会话能否真正使用推送内容（DSYNC-17）：模型请求经 SSH 反向隧道回到本机回放（与 WPL-011 相同），用模型请求判断远端 Agent 看到了什么，再实际调用 MCP 工具、`Skill`、`Agent`，检查工具结果；钩子在远端写标记文件。分三个时机记录：推送前已有的 task、推送前打开的新建任务页、推送后新建的 task。子智能体在三个时机都断言可用，并在已有 task 中实际调用 `Agent`；钩子单独在另一个推送前打开的新建任务页推送，断言该页第一条消息执行了钩子。

## Out of Scope

- 拉取方向（远端 → 本机），以及「推送到远端 / 拉取到本机」分段控件。
- 会话同步：需要新增 CLI 导出 / 导入协议，并处理 ID 重映射、绝对路径、附件、checkpoint 和子会话，另行设计。
- 记忆同步：两端记忆目录的 key 算法不同，需要先解决项目映射，另行设计。
- 「导出本地 / 导入本地」：设计稿没有定义文件格式。
- 项目级配置同步。
- Builtin Plugin、marketplace 缓存、插件 `data/`、敏感或路径类插件 options、MCP OAuth token、Bot 凭据的同步。
- 模型提供商的手动逐项同步与远端编辑（保持路线 A）。
- 设计稿以外的 Agent 运行开关不属于数据同步。记忆开关由[按设备设置工作区记忆](memory-settings.md)独立配置；`toolSearchMode` 等和 `~/.zcode/AGENTS.md` 另建 issue。
- 定时任务、闲时任务、highspeed 在远程场景下的问题，另建 issue。
- 同步基线、基于 mtime 的新旧判断、自动 / 定时同步。
- 设备上没有已打开项目时的模型配置下发。
- 记忆查看页按设备分组和远端记忆查看。

## Further Notes

- 决策依据：
  - 模型提供商只读，是因为设计稿（2026-08 下旬）早于 R3 §8.2 路线 A 的拍板（2026-09-07），按后者执行。
  - 只做推送、隐藏会话与记忆、不做导出导入、不建同步基线，都是 2026-10-16 评审的结论。
  - 设备过滤、待处理设备的显示、经连接向导连接、Provisioning 依赖 lane、命令来源合并、按行停止 marketplace 插件、旧入口覆盖 Docker、记忆查看页不变、迁移入口直达第一步，都是 2026-10-16 评审后与用户确认的结论。
  - E2E 改为在开发机上打 Linux 远端包、用本机 Docker Linux 容器模拟远端，同样是 2026-10-16 的结论。现有 harness 的远端本来就是同机容器，专用 Linux 服务器只提供 Xvfb、批量队列和真实账号所需的 VPN，本功能都不需要。Linux 服务器批次仍用于全量远程回归，但不是本功能的验收前提。
- 已知限制：
  - marketplace 插件不能锁定版本或降级。
  - marketplace 插件新建没有乐观并发校验：弹窗加载列表后目标端又装上同一插件时，推送仍会按新建流程重新安装，可能改写远端版本、启用状态和 options。修复需要 Agent 提供「不存在时才安装」的 RPC。
  - 远端的有效 MCP 来自 `~/.agents/mcp.json` 时，MCP 不能推送。
  - 远端同名命令位于 `~/.agents/commands` 时，该命令不能推送。
  - 钩子根级 `enabled` 只在本次推送有写入项时才会打开远端总开关；所有钩子定义都一致时，弹窗无法打开远端总开关，需要在远端钩子设置页直接打开。
  - 设备上没有已打开的项目时，模型配置不下发，也不能重试。
  - 设置服务的命令列表（`commandsService.list`）仍按回退规则读取：`~/.zcode/commands` 有命令时不再读 `~/.agents/commands`；CLI 运行时与本弹窗按合并规则读取。推送命令后，远端设置页的命令列表可能不再显示远端 `~/.agents/commands` 中的命令，运行时仍然可用。
  - Scope 菜单选中远端设备「用户」时，子智能体表单的模型只能选「继承默认」：source-settings 服务集合不含 model-selection（R3 §8.2）。页面不读取模型目录，也不显示「模型列表加载失败」。已存显式模型的子智能体保留原 model / 推理档位，推理控件显示「推理档位暂不可用」，不显示加载中。
  - 内置智能体的模型覆盖：本机清除覆盖（继承默认）后，推送不会清除远端的覆盖。两端 `modelId` 相同、Provider 不同时，「差异」行显示的两个模型名相同。插件智能体的模型覆盖不同步。
  - 远端 `agents-state.json` 有两个写入方：设置页的子智能体服务（写入队列只在单个服务实例内串行）和本弹窗的导入。两者没有共用的写入队列，同时写入时可能互相覆盖字段。2026-11-02 决定这次不收口（改动范围大）。
  - 没有版本号的条目无法判断哪一端较新，只能显示「内容不同」。
  - `~/.zcode/cli/config.json` 的多个写入方之间没有锁，同时写入时可能互相覆盖字段，见「写入安全加固」。
  - 技能或 inline 插件的目标目录之内嵌套了目标端的其他条目时，列表仍显示可勾选，推送时该项失败。
  - 本机 Docker E2E 是同机模拟，不覆盖真实跨机网络；Windows 开发机不在本机 runner 的支持范围内。
  - 推送内容在远端会话中的生效时机（DSYNC-17 实测）。远端 Agent 每个项目一个进程，每个会话只在创建时读取一次技能、MCP、插件和钩子：
    - 推送后在该项目新建 task，六类内容都能用，不需要重启远端 Agent。
    - 子智能体：远端 Host 监听远端文件，每轮把子智能体配置提供给 Agent，推送前已有的 task 和推送前打开的新建任务页在下一轮就能用，与本机一致；监听配置与本机相同（文件稳定 1 秒后发布，本机实测写入后约 1–1.5 秒生效）。见 `docs/subagent-runtime-refresh.md`「远程 workspace」。
    - 推送前已有的 task 拿不到新的技能列表、MCP 工具、插件和钩子。命令每条消息都重新读取，现有 task 也能用；技能不在列表里，但模型按名字调用 `Skill` 工具仍能加载。
    - 推送前已打开的新建任务页（预热会话）：推送技能、插件或钩子会让它重建，在该页发出的第一条消息就能用上；推送 MCP 不会，该页看不到新的 MCP 工具（本机设置页保存 MCP 也一样）。
    - 与本机对照（DSYNC-18 实测）：子智能体、MCP、插件、技能列表、钩子两端一致。一处不同：
      - 命令：本机设置页保存后输入框 `/` 菜单不刷新，推送会刷新；两端发送都能展开。
  - E2E 用的 test 包和开发用的 production 包（`pnpm dev:desktop` 配合 `pnpm prepare:remote-assets:linux` 的默认值）写在同一个发布目录。跑完 E2E 后回到开发调试前，需要重新打一次 production 包。
