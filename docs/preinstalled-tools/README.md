## 目标

文档插件依赖 Python、Poppler、Pandoc、qpdf 和 LibreOffice。用户电脑上不一定有这些程序。Agent 在任务中途安装它们，任务会变慢，也容易失败。

ZCode 在本机后台准备这些程序，供 Agent 使用。规则只有三条：

1. 某个工具的预装版本已就绪，且该工具的“Agent 使用预装版本”开关打开：Agent 用预装版本。
2. 否则：Agent 用这台电脑上已有的程序。
3. 两者都没有：插件先提示预装版本未就绪或已关闭，再由用户选择等待预装，或按插件原有方式处理（例如按 setup.md 安装）。五个工具的提示一致。

预装不替换插件依赖的工具和库，例如不把插件用的 Python 包换成别的包。插件的调用写法和工具缺失时的引导可以改。

增加一个工具时，只增加 catalog 条目、资源转换器和工具规格，不改预装链路的代码。链路代码中不出现按工具名写的分支。

## 术语

- **工具**：一组相关程序，用 `toolId` 标识，例如 `poppler`。
- **资源**：某个工具在一组平台上的一个固定版本归档，用 `resourceId` 标识。`resourceId` 对应的内容不变；内容变化必须使用新的 `resourceId`。
- **catalog**：随 App 构建内置的工具与资源清单。
- **入口**：固定入口目录 `bin/` 中的一个小脚本，把调用转给预装程序。
  - **抢先入口**：入口名和系统命令名相同，例如 `pdftoppm`。`bin/` 排在 Agent PATH 最前，所以 Agent 先找到它。
  - **专用入口**：入口名带 `zcode-` 前缀，例如 `zcode-python`。只有插件显式调用时才用到，不改变用户的 `python3`。
- **发布身份**：`production`、`preview`、`development`。每个发布身份使用独立的根目录。身份由 runtime 环境与 product flavor 决定，不由后端环境决定。
- **安装记录**：`tools/<toolId>/installation.json`。它是“这个工具当前装了哪个版本”的唯一事实。
- **自动预装**：全局开关，默认开启。决定 App 启动时是否自动准备。
- **Agent 使用预装版本**：每个工具一个开关，默认开启。决定 Agent 是否使用这个工具的预装版本。

## 事实源与派生结果

```text
唯一事实源（只由预装进程写）              派生结果（预装进程按左侧重建）
catalog（App 内置，只读）            ──► 每个工具的目标资源
设置：自动预装                       ──► App 启动时是否排队准备
设置：每个工具的“Agent 使用预装版本” ─┐
安装记录 tools/<id>/installation.json ─┴► bin/ 中该工具的入口
                                          入口存在 = 记录有效且开关打开
Agent PATH = bin/ + 原 PATH           ← Host 启动 Agent 时注入一次，之后不变
```

- 入口只由“安装记录 + 开关”推导，不读取 catalog。App 升级后，旧版本的入口在新版本就绪前仍然有效（见“升级”）。
- 安装记录保存入口定义。入口定义在发布时从资源清单复制过来，所以旧版本的入口仍按旧版本的定义生成。
- Main、Host 和 UI 不保存“已安装”或“开关”的第二份事实。

## 目录

```text
<数据根>/.zcode/preinstalled-tools/<发布身份>/
├─ bin/                                  固定入口目录，只由预装进程写
│   pdftoppm pdftotext pdfimages pdfinfo qpdf pandoc zcode-python zcode-soffice
│   （Windows 上每个入口是 <name>.exe 与 <name>.shim，另有 .retired/）
└─ tools/<toolId>/
    ├─ installation.json                 安装记录，即发布点
    ├─ versions/<resourceId>/            版本目录：解压后的资源
    └─ staging/                          临时区
```

- 数据根默认是用户主目录；自定义数据目录的规则不变。
- 路径中没有 App 版本。App 升级时，某个工具的目标 `resourceId` 没变，就直接复用已有安装，不重新下载。
- 每个工具的子树互相独立。准备、清理、删除和占用检查只作用于本工具。
- 工具需要的可写目录放在自己的版本目录里，随版本创建和删除。例如 Python 的附加区，见 [Python 规格](python.md#附加区)。

## Catalog 与资源清单

catalog 是一个工具列表。每个工具有 `toolId`、`displayName` 和若干资源。每个资源的清单字段如下。

| 字段                              | 含义                                                                                                     |
| --------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `toolId`、`resourceId`、`version` | 资源身份                                                                                                 |
| `platforms`                       | 适用平台列表，每项是 `{platform, arch}`                                                                  |
| `binaryArch`                      | 程序本身的架构。可以和适用平台不同，例如 x64 资源声明给 Windows arm64，靠系统仿真运行                    |
| `archive`                         | 格式固定为 `tar.gz`；字节数、SHA-256、`path`（相对于下载基址的 POSIX 路径，见“下载地址”）                |
| `installedSizeBytes`              | 解压后的字节数，也是解压时的上限                                                                         |
| `requiredFiles`                   | 安装后必须存在的相对路径，必须包含全部入口目标                                                           |
| `rewrite`                         | 可选。安装时要改写的文件：`{path, placeholder, mode}`，`mode` 为 `text`、`binary` 或 `binary-dir-prefix` |
| `entries`                         | 入口列表：`{name, target, args, env}`。`env` 每项为 `set`、`default`（仅在调用方未设置时生效）或 `unset` |
| `runtimeChecks`                   | 运行检查列表，至少一项：`{entry, args, expectedOutput, timeoutMs}`                                       |

路径字段都是资源内的 POSIX 相对路径，不得有空段、`.`、`..`、反斜杠或盘符。`args` 和 `env` 可以使用下列占位符，由预装进程在使用时替换：

| 占位符                                   | 值                                                          |
| ---------------------------------------- | ----------------------------------------------------------- |
| `${INSTALL_DIR}`、`${INSTALL_DIR_URL}`   | 版本目录的绝对路径，以及它的 file URL                       |
| `${CHECK_TEMP_DIR}`、`${CHECK_TEMP_URL}` | 每次运行检查独立创建的临时目录及其 file URL，检查结束后删除 |

`entries[].target` 是相对于版本目录的路径。`env` 每项使用 `{name, action, value}`，`action` 为 `set` 或 `default`；`unset` 使用 `{name, action}`，不带 `value`。`archive` 使用 `format`、`sizeBytes`、`sha256` 和 `path` 字段。

catalog 校验：

- `toolId` 唯一；同一工具在同一平台上最多只有一个资源。
- 所有工具的入口名互不相同。名字以 `zcode-` 开头的是专用入口，其余是抢先入口。
- `requiredFiles` 包含所有入口目标；`runtimeChecks[].entry` 必须是本资源的入口。
- catalog 只接受 `archive.path`，不接受完整下载地址、显式下载列表或地域分组。

### 下载地址

catalog 不写完整地址。下载地址由 Main 把 `archive.path` 拼到有序的下载基址列表上得到，每个基址一个候选：

```text
候选地址 = <基址>/<archive.path>（path 按段做 URL 编码）

基址列表：
  ZCODE_PREINSTALLED_TOOLS_CDN_BASE_URL 已设置 ──► 只用它（逗号分隔，按书写顺序）
  未设置 ──► https://cdn-zcode.z.ai/zcode/preinstalled-tools
```

- 2026-11-06 用户确认默认只使用 `cdn-zcode.z.ai`，不再按语言或时区选择 CDN。覆盖变量中的候选仍按配置顺序尝试，重复基址只保留第一次出现的位置。
- 规则不区分 `ZCODE_ENV` 和发布身份。需要从内网或其他服务器下载时，启动 App 前设置 `ZCODE_PREINSTALLED_TOOLS_CDN_BASE_URL`。它与 `ZCODE_REMOTE_ASSET_CDN_BASE_URL` 相互独立：远程资源按 App 版本分目录，预装资源按 `resourceId` 分目录。
- 变量中有不合法的地址（不是 http 或 https，例如漏写协议）时，工具描述照常取自 catalog，所有工具的目标为 `null`，Main 写错误日志；不回退到官方基址，避免设置写错时静默改用公网。这不表示工具已移出 catalog：已安装的版本、入口和 Python 附加区保持不变，状态按“没有目标但有已安装版本”显示为 `ready`。
- 服务器目录结构由发布命令决定，见“资源制作与发布”。官方 CDN 与内网服务器使用相同的结构，所以同一个 catalog 换基址即可下载。

| qpdf        | `qpdf-12.4.2-darwin-arm64-r1`             | `qpdf-12.4.2-darwin-x64-r1`             | `qpdf-12.4.2-win32-x64-r1`             |
| Pandoc      | `pandoc-3.1.12.2-darwin-arm64-r1`         | `pandoc-3.8.1-darwin-x64-r1`            | `pandoc-3.13-win32-x64-r1`             |
| Poppler     | `poppler-26.10.0-darwin-arm64-r2`         | `poppler-26.10.0-darwin-x64-r1`         | `poppler-26.10.0-win32-x64-r1`         |
| LibreOffice | `libreoffice-26.8.1-darwin-arm64-r2`      | `libreoffice-26.8.1-darwin-x64-r2`      | `libreoffice-26.8.1-win32-x64-r3`      |

- 平台选择只依据资源已声明的 `platforms`。Windows arm64 仅有 Pandoc、Poppler 的 x64 仿真条目；本批没有 Linux 资源，不为缺失平台推导目标。
- 复用现有串行准备、大小与 SHA-256 校验、运行检查和原子安装记录发布，不增加另一条安装路径。
- 普通 E2E 显式注入五工具的空资源清单；资源类 E2E 使用各自夹具。仅真实 CDN 验收用例使用内置清单和默认 CDN，避免无关测试在启动时批量下载。
- CDN 字节核对不替代各平台原生验收或法务结论；原有相关待办保留各自状态。

装配：

- Main 在 App 启动时读取内置 catalog，按当前 `process.platform` 和 `process.arch` 为每个工具选出资源，没有资源的工具目标为 `null`。
- Main 按上一节生成下载地址。
- Main 把装配结果交给预装进程。Host 不接收 catalog，也不等待这一步。
- 内置 catalog 保留本期五个工具描述；没有可用资源的工具使用空 `resources`，不放示例地址或未验证的资源身份。本文的“无发布资源”不表示另设 UI 工具列表。
- 仅在打开 E2E 编译开关的构建中，`ZCODE_E2E_PREINSTALLED_TOOLS_CATALOG` 可以覆盖内置 catalog。生产构建即使继承了这个变量也忽略它。
- catalog 本身无法读取或未通过校验时，清单不可用：Main 写错误日志，交给预装进程的工具列表为“不可用”，而不是空列表。工具归属未知，预装进程不清理无主入口，也不删除任何工具目录；对话框没有工具卡片。下次清单可用的启动再按正常规则对齐。空列表只表示 catalog 确实没有工具。

## 进程与状态

预装进程沿用首期设计：

- 它是一个独立的常驻 utilityProcess。Main 在 App 启动时拉起它，退出时通知它收尾，并在窗口与它之间转发消息。Main 不保存预装状态。
- 它不放在 Host 里，因为 Host 随窗口创建和销毁，本机工具不属于任何工作区。它也不放在 scheduler 里，因为 scheduler 不发 HTTP，下载故障也不能连带停掉定时任务。
- 它在报告初始化完成后意外退出时，Main 重新拉起它。新进程清理 staging，重新核对磁盘，但不自动下载。
- 它在报告初始化完成前就退出时（例如安装包损坏导致模块加载失败），视为启动失败。Main 不再拉起它，等待中和之后的查询与操作都以错误结束，直到下次 App 启动。立即重拉只会形成无上限的启动循环。对话框据此显示启动失败提示，见“UI”。
- 仅在打开 E2E 编译开关的构建中，`ZCODE_E2E_PREINSTALLED_TOOLS_EXIT_BEFORE_INIT=1` 让预装进程在初始化前退出，用于验证上一条（PT-30、PT-31）。生产构建即使继承了这个变量也忽略它。
- 初始化时的目录或设置故障留在进程内，表现为可重试的失败状态，进程不退出，避免反复重启。

进程内部：

```text
预装进程（每个发布身份一个）
├─ 设置：自动预装、每个工具的“Agent 使用预装版本”
├─ 准备队列：串行，一次只执行一个工具
├─ owner[python]       状态、在途操作、删除
├─ owner[qpdf] …       同上
└─ 入口维护：按“安装记录 + 开关”写 bin/
        ▲ 命令 {type, toolId}              │ 完整状态 {autoInstallEnabled, tools[]}
        └──────────── Main 转发 ◄──────────┘──► 对话框
```

每个工具的状态：

| 字段              | 含义                                                                                                                                                                  |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `toolId`          | 工具身份                                                                                                                                                              |
| `target`          | 目标资源：`resourceId`、`version`、`archiveSizeBytes`、`installedSizeBytes`；无资源时为 `null`                                                                        |
| `installed`       | 已安装资源：`resourceId`、`version`、`installedSizeBytes`；未安装时为 `null`                                                                                          |
| `status`          | `ready`：已安装的就是目标，或没有目标但有已安装版本。`not-installed`：目标未安装，此时可能装着旧版本。`preparing`：目标在队列中或正在准备。`failed`：最近一次准备失败 |
| `phase`           | `queued`、`downloading`、`verifying`、`extracting`、`checking`                                                                                                        |
| `downloadedBytes` | 下载阶段的已下载字节数                                                                                                                                                |
| `error`           | `network`、`interrupted`、`disk-space`、`checksum`、`extract`、`runtime`、`unsupported`                                                                               |
| `deletionBlocked` | 最近一次删除因占用被拒绝                                                                                                                                              |
| `agentEnabled`    | 该工具的“Agent 使用预装版本”开关                                                                                                                                      |
| `entryOutOfSync`  | 入口尚未与已保存事实对齐；独立于准备错误，成功对齐后清除                                                                                                              |

命令：`set-auto-install {enabled}`、`set-agent-enabled {toolId, enabled}`、`sync-entries {toolId}`、`prepare {toolId}`、`cancel {toolId}`、`delete {toolId}`。preload、Main 和预装进程三处都按 schema 校验；只有主窗口可以发送命令。

- 任何变化都推送完整状态。窗口先订阅推送再查询初始快照；收到推送后，忽略迟到的初始快照。命令回执不覆盖推送的状态。
- 两个开关都保存在现有本机设置中，只由预装进程写入：自动预装沿用 `preinstalledToolsAutoInstall`；每个工具的开关新增 `preinstalledToolsAgentDisabled`，内容是被关闭的 `toolId` 列表，缺省表示全部开启。保存走现有设置写队列。保存成功后立即更新内存中的唯一开关值，再对齐入口并推送状态；入口 IO 失败也不得恢复旧开关值。保存失败时保留原值，在对话框内提示重试，不弹 Toast。

## 准备

### 队列

- 真正的 App 启动且自动预装开启时，把目标未安装的工具按 catalog 顺序加入队列。用户打开自动预装开关时也这样做。预装进程崩溃重启后不自动排队。
- 用户点“下载”“更新”或“重试”时，把该工具加入队列。重复请求加入已有的在途操作，不重复下载。
- 队列一次只执行一个工具，以免同时占满带宽和磁盘，空间检查也更准确。
- “取消下载”只影响该工具：正在执行就中止，在队列中就移出。其他工具继续。
- 关闭自动预装不取消已排队或正在进行的准备，只影响以后的 App 启动。
- 删除请求等该工具的在途操作结束后再执行。

### 安装事务

```text
排队 → 下载（含校验） → 解压 → 改写与重签 → 移入版本目录 → 运行检查 → 写安装记录 → 写入口
                                                                     ▲ 唯一发布点
发布前失败或取消：删除本次的版本目录和 staging；已安装的旧版本不受影响，继续使用
发布后入口对齐失败：保留记录和版本目录，标记 entryOutOfSync，等待重试或下一次入口维护
```

1. **平台检查**：当前平台不在 `platforms` 中时，下载前报告 `unsupported`。
2. **空间检查**：读取 staging 所在文件系统的可用空间，至少需要归档字节数与解压字节数之和。任何阶段出现 ENOSPC，都报告 `disk-space`，不被阶段错误覆盖。
3. **下载**：沿用首期的下载规则。
   - 每次准备新建一个 Host 网络适配器实例，读取当前的代理、noProxy 和自定义 CA。同一次准备的所有候选地址共用这份网络设置。下次重试重新读取。
   - 按排好的顺序尝试候选地址。每个候选都从零写一个新临时文件，并重新计算大小、SHA-256 和进度。失败就清理并尝试下一个；取消立即停止。
   - 所有候选都失败时，报告最深入的错误：校验失败优先于中断，中断优先于连接失败。日志分别记录每次失败。
   - 响应正常结束但大小或摘要不符，是 `checksum`；响应中途断开，是 `interrupted`。
   - 不续传。取消、失败或退出后，下次从零开始。
4. **解压**：流式解压 tar.gz。保留符号链接和可执行权限。拒绝越界路径、指向资源外的链接和不支持的条目类型。展开字节数超过 `installedSizeBytes` 时失败。格式或路径非法时报告 `extract`。
5. **必需文件**：`requiredFiles` 缺失时报告 `checksum`。
6. **改写与重签**：
   - 对 `rewrite` 中的每个文件，把占位符替换为最终版本目录的绝对路径。`binary` 模式保留每个 NUL 终止字符串的完整后缀，替换其中所有占位符后，在整段末尾用 0 字节补齐原长度，不在路径前缀后插入 NUL。文件末尾没有 NUL 时，以文件末尾为该段边界。长度按 UTF-8 字节计算；版本目录路径比占位符长时报告 `unsupported`，并在日志中写明两个字节数。`text` 模式直接替换。
   - `binary-dir-prefix` 模式把占位符原位换成版本目录的绝对路径，用 `/` 补足占位符的原长度，不移动后缀，也不写入 0 字节。每处占位符后面必须是 `/`、NUL 或文件末尾，否则打包失败。只能在 recipe 中逐个文件显式声明，转换器不能从 `has_prefix` 或等价元数据自动选择；未声明时保留原 `binary` 模式。本期 Windows 资源不能声明该模式，声明时打包失败。长度超出和 macOS 重签规则与 `binary` 相同。
   - 在 macOS 上，改写过的 Mach-O 文件用 `codesign --force --sign -` 重新做 ad-hoc 签名。未改写的文件保留上游签名。
   - 没有声明 `rewrite` 的资源跳过这一步。
7. **移入版本目录**：把 staging 中的内容 rename 到 `versions/<resourceId>`。目标位置有无记录的残留时，先做占用检查再删除。
   - Windows 上，rename 返回 `EPERM`、`EBUSY` 或 `EACCES` 时，等待后重试：等待时间从 50 毫秒起逐次加倍，单次最多 2 秒，从第一次失败算起最多 15 秒。每次重试写一条 warn 日志，包括错误码、第几次和已等待的时间。期间取消立即停止。15 秒后仍失败，按原错误报告 `runtime`。其他错误和其他平台不重试。
   - 原因：Windows 上目录里只要有一个文件被别的程序打开，而且打开时没有允许删除，整个目录就不能改名。安全软件会在新文件写出后一段时间内打开它们扫描。2026-11-05 在一台装有金山毒霸铠甲防御和飞连安全模块（Defender 为被动模式）的 Windows 11 x64 上实测：Poppler 四次安装都在这一步失败，错误为 `EPERM`；用同样的归档解压后等 2 秒再改名，Poppler 5 次中 3 次、qpdf 5 次中 5 次失败，全部在重试后成功，最长等待 1594 毫秒。立即改名的 10 次都成功，说明占用在写完后稍晚才开始，所以解压耗时较长的资源更容易撞上。被哪个程序占用、占用的是文件还是目录，没有直接证据。见工单 ZCT-2118196504844603392。
8. **运行检查**：按入口定义执行每一项检查。目标、参数和环境与入口完全相同，`${CHECK_TEMP_*}` 指向本次检查的临时目录。stdout 与 stderr 合并后必须包含 `expectedOutput`。超时、非零退出或输出不符都报告 `runtime`，包括通过系统仿真运行的资源。取消和超时都要结束整棵进程树：macOS 和 Linux 上检查在独立进程组中启动，超时或取消时结束整个进程组，因为入口 `exec` 成目标后，只结束直接子进程会留下目标派生的后代（例如 Linux LibreOffice 的 `soffice.bin`）；Windows 上入口是 shim，结束 shim 后，它的作业对象会结束目标及其后代（见 [Windows 入口 shim](windows-entry-shim.md#运行检查)）。调用在 stdout 与 stderr 关闭后才返回，之后再清理。主动脱离进程组的后代不在此范围内。失败日志记录资源的 `binaryArch` 和本机架构 `hostArch`，便于导出日志后排查；不根据这些失败结果推断仿真是否受支持，也不按工具区分错误。
   - `timeoutMs` 必须容纳系统对新文件的首次安全检查。macOS 在首次加载新写入的程序和库时会逐个检查，期间进程停在 dyld 映射库的阶段，没有输出。2026-10-30 在 macOS 26.5.2（arm64）上实测：Poppler 的 `pdftoppm -v` 首次约 21～24 秒、再次 0.02 秒；Python 导入检查首次约 45～63 秒、再次约 1.8 秒。检查结果按文件缓存，目录改名后仍然有效。
   - Windows 上 Microsoft Defender 实时防护在首次执行新写入的大程序时会先扫描完整个文件，期间进程不启动。2026-11-03 在 Windows 11（x64，Defender 默认设置）上实测：Pandoc 的 `pandoc.exe`（约 240 MB）运行检查有时约 0.24 秒，有时 9.2～10.04 秒；Defender 日志记录的对应扫描为 8593～11328 毫秒，结束时刻与检查结束时刻一致。原 10 秒上限因此偶发失败。何时跳过扫描、扫描结果在改名后是否仍然有效，未确认。
   - 检查在最终版本目录中运行，所以检查通过后，入口第一次被调用时不再等待系统检查。不另做预热。
9. **发布**：先用“临时文件 + rename”写安装记录，rename 的重试规则与第 7 步相同。安装记录是唯一发布点。然后由共用函数按安装记录和已保存的开关全量对齐该工具的入口；关闭时撤入口，打开时写入口。入口对齐失败只标记 `entryOutOfSync`，不撤回已发布的安装。
10. **收尾**：删除 staging。发布后的收尾失败不撤回已发布的安装。

阶段与 UI 的对应：步骤 3 是 `downloading`，摘要校验是 `verifying`，步骤 4～7 是 `extracting`，步骤 8 是 `checking`。

安装记录字段：`schemaVersion`、`toolId`、`resourceId`、`version`、`platform`、`arch`、`installationDir`、`installedSizeBytes`、`requiredFiles`、`entries`（资源清单中的入口定义，占位符在写入口时替换）、`installedAt`。其中 `installedSizeBytes`、`requiredFiles` 和 `entries` 从发布时的资源清单复制，所以 App 升级后仍能核对和使用旧版本。读取时严格校验 schema，并核对 `installationDir` 是 `versions/<resourceId>`、记录中的 `requiredFiles` 都存在。

### 取消与发布的顺序

沿用首期规则：

- 在最后一次取消检查和准入发布之间，没有异步等待。
- 已准入的发布不中途撤销。和它重叠的取消排在它的结果之后：写入成功就保持已就绪；写入失败就报告真实失败并清理。
- 取消在准入发布之前到达时，中止操作；清理完成、释放旧操作后，才推送未安装状态，避免紧接着的重试加入已取消的旧操作。
- 旧操作晚到的进度、错误或完成消息，不覆盖新操作的状态。

## 升级

新版本就绪前，Agent 继续用已安装的旧版本。

```text
旧 App：python 记录 = r1，入口 zcode-python → r1
新 App：catalog 中 python 的目标 = r2，其余工具目标不变
  其余工具：记录 = 目标 → 不做任何事，入口一直可用
  python：记录 r1 ≠ 目标 r2 → status = not-installed，installed = r1
     自动预装开启 → 排队准备 r2；关闭 → 等用户点“更新”
     准备期间：入口仍指向 r1，Agent 照常使用
     r2 发布：原子替换安装记录 → 重写 zcode-python 指向 r2
     下次真正的 App 启动：删除 r1 的版本目录（有进程占用就保留到以后）
```

- 新版本准备失败时，旧版本继续可用，卡片同时显示失败原因和当前使用的版本。
- 升级期间使用的旧版本没有经过新 App 插件的验收。如果新插件依赖新版本的功能，调用会失败，由插件的回退处理：LibreOffice 换用系统版本重跑一次，Python 按 [Python 规格](python.md#出问题时)处理。

## 入口

### 注入

- 桌面 Local Host 启动本机 Agent 时，把 `<发布根>/bin` 加到 Agent PATH 的最前面，并注入 `ZCODE_PREINSTALLED_TOOLS_AVAILABLE=1`。路径由数据根和发布身份按固定规则算出，不依赖 catalog，也不等待预装进程。
- 本机桌面总会注入。当前平台没有资源时，插件仍可能提示“帮助 → 预装工具”，对话框里显示“当前版本暂未提供此工具”。
- 远端工作区（SSH、WSL、Docker）、Web 服务端和独立 CLI 不注入。Agent 进程管理在 spawn 边界只采用执行端 Host 给出的值，不继承 shell 或部署命令中的同名值。
- Agent 侧的细节见 [Agent 侧入口](../../apps/zcode-cli/docs/design/v2/preinstalled-document-tools.md)。

### 入口文件

- 对齐成功时，入口存在，当且仅当该工具的安装记录核对通过，且“Agent 使用预装版本”开关打开。IO 失败造成的暂时差异由 `entryOutOfSync` 明确表示，不把派生结果当作第二份开关事实。
- 入口内容由安装记录中的入口定义生成，目标用绝对路径。
- POSIX：一个 sh 脚本，设置 `env` 后用 `exec` 运行目标并追加 `args`，再传入调用方参数。
- Windows：每个入口是一个 shim 可执行文件 `<name>.exe` 加一份配置 `<name>.shim`。shim 读取配置，设置环境，启动目标，返回目标的退出码。所有调用方（Git Bash、PowerShell、cmd、Python 列表参数、Node `execFile`、MCP 的 cross-spawn）都按普通可执行文件找到它。没有 sh 入口和 `.cmd`。配置格式、shim 行为、写入与撤销顺序见 [Windows 入口 shim](windows-entry-shim.md)。
- 每个入口文件都用“临时文件 + rename”写入。Windows 上运行中的 `.exe` 不能被覆盖，撤下和替换时先改名移走，见 [Windows 入口 shim](windows-entry-shim.md#bin-目录与入口维护)。

### 维护

| 事件             | 入口操作                                                                                            |
| ---------------- | --------------------------------------------------------------------------------------------------- |
| 预装进程初始化   | 按每个工具的“安装记录 + 开关”全量重建：写入应有的入口，删除多余的文件。记录无法核对的工具不保留入口 |
| 发布新版本       | 先写安装记录，再按已保存开关全量对齐入口（打开时写入，关闭时撤销）                                  |
| 关闭某工具的开关 | 保存设置后删除该工具的入口                                                                          |
| 打开某工具的开关 | 保存设置后，如果有有效记录就写入口                                                                  |
| 删除             | 先删入口，再做其他事（见“删除与清理”）                                                              |

- 发布、开关、初始化及重试共用同一个按“安装记录 + 已保存开关”全量对齐单个工具入口的函数；失败标记的设置和清除均在该函数中完成，不按事件维护不同的开关副本。
- 入口写入或删除失败时，不回滚安装记录或开关设置。预装进程把该工具标记为 `entryOutOfSync` 并推送完整状态，不复用准备失败的 `error`。
- 卡片提示“开关已保存，但尚未生效，请重试。”，旁边提供独立“重试”按钮，不替换原有下载、更新或删除按钮；中英文文案进入国际化资源，不向用户暴露“入口”术语。日志记录工具、失败方向和 IO 错误。
- 重试命令 `sync-entries {toolId}` 只按安装记录和已保存开关重建该工具的入口，不下载、不改设置。之后任何入口维护成功都清除标记；不加定时自动重试，后续发布、升级或初始化自然恢复时也必须使用已保存值。
- 删除第一步撤入口失败时，删除中止，安装记录和版本目录保留，并显示同样提示。成功路径、占用检查、发布与版本回收顺序保持不变。

写入顺序保证：任何一步崩溃后，最坏的结果是少了入口，不会出现指向已删除程序的入口。下次初始化重建即可恢复。这一点由写入顺序保证，不依赖等待时间。

### 生效范围

- 每条 Bash 命令都开一个新 shell，重新按 PATH 查找程序。所以入口的增删从 Agent 的下一条命令起生效，已打开的会话也一样，不需要重启 Agent。
- 正在运行的命令不受影响。一条命令内部如果多次调用同一程序，shell 可能缓存了旧路径；入口在中途被删除时，这次调用会失败，下一条命令会恢复正常。
- 覆盖：Agent 的 Bash 和后台 Bash、hooks、Agent 启动的 MCP stdio 服务（继承 Agent 环境，MCP 配置自行设置 PATH 时除外），以及它们启动的子进程，例如 pdf2image 调用的 `pdftoppm`。
- 不覆盖：App 的终端面板、远端工作区、Web 服务端、独立 CLI。

### 已知风险，需要实测

- Windows Git Bash 的登录 profile 会改变 PATH 顺序（已实测），CLI 在快照和退回路径中恢复 `<bin>` 的最前位置，见 [Agent 侧入口](../../apps/zcode-cli/docs/design/v2/preinstalled-document-tools.md)。
- 其他 shell 在 Bash 快照创建失败时，命令退回 `-c -l` 执行，rc 文件可能改变顺序（推断）。
- Windows 原来的 `.cmd` 入口在真机上有两个问题：不经 shell 的调用方找不到入口；运行中删除入口时调用方得到退出码 1。经用户确认改用 shim，原因与实测见 [Windows 入口 shim](windows-entry-shim.md#为什么改)。shim 的参数透传、退出码、撤下与结束进程树，按该文的验收表在 Windows 真机上验证。

## 删除与清理

### 删除

```text
用户删除某个工具（确认框确认后）
 1. 删除 bin/ 中该工具的入口               → 新的调用改用系统版本
 2. 检查进程占用：程序路径在版本目录内的本用户进程
    ├─ 有占用或无法确认 → 恢复入口；状态保持，卡片提示“正在被 Agent 使用”
    └─ 无占用 → 3. 删除安装记录 → 4. 删除版本目录
```

- 删除只作用于这一个工具，回收它所有版本的目录。删除不改变两个开关。
- 同一工具的准备、删除和清理由该工具的 owner 串行执行。App 单实例运行，每个发布身份只有一个预装进程，因此不需要磁盘上的锁或标记。
- 进程占用检查沿用首期探针：macOS 用 `lsof` 检查映射，Linux 读 `/proc/<pid>/exe`，Windows 读进程的可执行路径。探针超时或失败都视为“无法确认”，不能据此允许删除。
  - Windows 例外：系统进程和提权进程读不到路径（例如输入法 `ctfmon`），这类进程常驻，不能一律视为“无法确认”，否则工具永远删不掉。这时比对进程名：与版本目录内某个文件同名（不区分大小写）就算占用；否则不算。遗留风险：不覆盖读不到路径且程序已改名的进程。
  - Linux 例外：ssh-agent 这类不可转储（non-dumpable）的本用户进程，读 `exe` 会被拒绝（EACCES）。这时改读 `/proc/<pid>/cmdline` 的 argv[0]：它是绝对路径，且按真实路径落在版本目录内，就算占用；否则不算。入口用绝对路径 `exec` 目标，所以经入口启动的程序 argv[0] 一定在版本目录内。读取 `exe` 的其他失败仍视为“无法确认”。
- 遗留风险：某个调用已经找到入口、还没启动真正的程序时，正好执行到第 2 步。这次调用会报“找不到文件”，下一条命令会改用系统版本。LibreOffice 统一入口的“失败后用系统版本重跑一次”会接住这种情况。
- 中途崩溃：安装记录删除前崩溃，工具仍然可用，下次初始化重建入口；安装记录删除后崩溃，残留目录由启动清理删除。

### 启动清理

- 每次初始化都清空每个工具的 staging。
- 真正的 App 启动时（预装进程崩溃重启不算），对每个工具执行同一条规则：只保留安装记录指向的版本目录；其余目录先做占用检查再删除，有占用就保留到以后。这条规则同时覆盖升级后的旧版本、删除中途的残留和安装中断的残留。
- 当前 catalog 中没有的工具：撤销入口，再按同一规则删除它的全部目录。只有清单可用时才这样判断；下载基址不合法只让目标为 `null`，不算移出 catalog；清单不可用时不做这项清理。
- “清除所有数据”不删除预装资源。资源管理器的存储页把它们单独归类显示，不提供清理。

## 插件调用规则

插件只改调用方式和缺失时的引导，不替换依赖。各工具的写法见对应规格。

- **抢先入口的工具**：插件继续使用原来的命令名。命令找不到时，按下面的“工具不可用时的引导”处理。
- **Python**：运行脚本和安装包都用 `"$(command -v zcode-python || command -v python3)"`。PowerShell 脚本先找 `zcode-python`，再用原有的 Python 选择逻辑。工程门禁禁止 skills 中出现裸 `python` 或 `python3` 调用。见 [Python 规格](python.md#插件调用规则)。
- **LibreOffice**：继续通过插件统一入口调用。见 [LibreOffice 规格](libreoffice.md#插件统一入口)。
- **工具不可用时的引导**（五个工具一致；Poppler 包括 pdf2image 报告找不到 Poppler 的情况）：
  - 有 `ZCODE_PREINSTALLED_TOOLS_AVAILABLE` 时，先停下，不安装任何东西。说明“预装版本未就绪或已关闭，请在 帮助 → 预装工具 中查看”，再由用户选择：等待准备（或打开开关），或按插件原有方式继续，例如让 Agent 按 setup.md 或依赖说明安装，或换用插件已有的替代做法。
  - 没有这个变量时，保持插件原有的安装引导。
  - Agent 只知道“预装版本能不能用”，不区分“还没装好”和“开关已关闭”。准确状态在对话框中查看。
- 不改系统提示词，不改 App ↔ Agent 协议，不新增 Agent 工具。不自动暂停、恢复或重发任务。工具就绪后由用户让 Agent 继续。

## 资源制作与发布

- 打包工具位于 `scripts/preinstalled-tools/`：`common/` 放公共能力（归档、摘要、发布清单、二进制结构检查、许可与来源汇总、构建前缀扫描）；每个工具一个目录，放转换器和 recipe。
- recipe 固定全部输入：上游文件的 URL 与 SHA-256，可用时还有签名。转换器先产出不含下载地址的资源描述；发布命令补上 `archive.path`，生成 catalog 条目。
- `archive.path` 固定为 `<toolId>/<resourceId>/<resourceId>.tar.gz`，由发布命令按资源身份生成，不接受手填。上传时归档放在每个基址下的这个路径。
- 同一路径上传后不再修改。旧 `resourceId` 不删除，供仍在使用旧 catalog 的 App 版本下载。归档内容有任何变化都必须使用新的 `resourceId`。
- `runtimeChecks` 写在资源描述和 catalog 中，不在归档里。只调整 `runtimeChecks`（例如超时）时，归档字节和 CDN 路径都不变，不换 `resourceId`；重新运行转换器，核对归档的大小与 SHA-256 与原值一致，再重新生成 catalog 条目。
- conda 转换公共层同时读取旧 `info/has_prefix` 与新 `info/paths.json` 的 `prefix_placeholder` / `file_mode`。两种元数据同时存在时必须一致；裁剪后只为实际保留的文件生成 `rewrite`，不能留下指向已删除 pkgconfig、头文件等内容的声明。
- conda 包内 recipe 只有 HTTP 源码地址时，输入 recipe 可用 `sourceArchives` 显式补充 HTTPS 资产（文件名、URL、大小、SHA-256）。只接受原地址同 host/path/query 的 HTTP → HTTPS 等价，摘要必须与原 recipe 一致，并实际下载或读取缓存核对大小与摘要；不自动猜地址、不允许任意换源。原 HTTP 地址保留在产物来源证明或核验日志，`SOURCES.json` 写已核对的 HTTPS 地址。
- conda 许可优先取包内 `info/licenses/`；包将许可放在 `share/licenses/` 等载荷路径时，由 recipe 显式列出相对路径。缺少完整许可文本时，只能用固定官方 URL、大小和 SHA-256 的显式补充输入补齐；构建 recipe 自身的许可不能冒充库的许可，许可缺失仍拒绝制作。这不替代法务确认。
- 打包时必须通过的检查，任一项失败就不产出：
  - 资源根目录的身份文件 `zcode-tool-resource.json` 与 recipe 一致。运行时只依赖 catalog 中的 SHA-256，不再读取这个文件。
  - 所有 Mach-O 的最低系统版本不高于 13.0（桌面最低支持的 macOS 版本）。
  - 所有 ELF 需要的 GLIBC 不高于 2.28。
  - 所有 PE 的架构与 `binaryArch` 一致。例外：recipe 可以把不会被加载执行的上游数据文件（例如启动器模板）声明为架构例外，每项写明精确相对路径、SHA-256、来源和用途，不允许通配符。
    - 文件必须与已核对来源（官方签名或 recipe 固定的摘要）中的文件逐字节相同。上游升级导致摘要变化时，打包失败，重新审阅后才能更新 recipe。
    - 只豁免架构一致性检查，其他打包检查照常执行。
    - 入口目标、运行检查目标、`rewrite` 目标，以及从入口目标按导入表可达的依赖库，不能声明为例外。导入表不能穷尽动态加载的组件，其余运行时用途仍由声明和审阅核对。
    - 声明的路径不存在、摘要不符，或文件本来就能通过架构检查、不需要例外时，打包失败。
  - 资源中不出现本次打包环境的路径（staging、临时目录、缓存目录、用户主目录和用户名）。
  - 已知的重定位占位符（例如 conda 的前缀占位符）只能出现在已声明 `rewrite` 的文件中。
  - 上游构建路径：recipe 可以声明上游二进制中的诊断构建路径前缀，并写明来源。只有与已核对来源（官方签名或 recipe 固定的摘要）中的上游文件逐字节相同的文件可以包含这些前缀；打包时生成或添加的文件不能包含任何未声明的绝对构建路径。资源视图、`fonts.conf`、`pyvenv.cfg`、`constraints.txt` 和 `LICENSES/` 等生成或添加的文件不适用上游路径豁免。本次打包环境的路径与未声明的重定位占位符始终拒绝，不受豁免影响。
  - Python 字节码（`.pyc`）是唯一可以继承上游路径豁免的生成文件，必须同时满足：
    - 对应 `.py` 来自已核对来源（官方签名或 recipe 固定摘要），且文件未改动。
    - 用资源自带的解释器、固定的编译参数（`unchecked-hash`、去打包前缀和优化级别）以及 `PYTHONHASHSEED=0` 独立重编译，结果与该 pyc 逐字节相同。
    - pyc 中出现的每个上游路径前缀，都已在 recipe 中声明，并且也出现在对应 `.py` 中。
    - 只有含已声明上游前缀、需要继承豁免的生成 pyc 才执行这项证明；不含构建路径的 pyc 走普通扫描。重编译结果不一致时打包失败，日志列出具体文件，不退回直接允许。
    - 本次打包环境路径和未声明 `rewrite` 的占位符在 pyc 中仍一律拒绝；其他生成文件不能使用此例外。检查按 `.pyc` 文件格式放在公共层，不按工具名分支，不增加通用“派生文件”框架。
  - 运行时不依赖构建路径，由运行检查和含空格与中文的安装路径验收证明，不以静态扫描为证明。
  - 根目录有 `LICENSES/`（所有组件的许可证文本和 NOTICE）和 `SOURCES.json`（每个组件的上游源码地址与 SHA-256）。
  - `requiredFiles` 全部存在；归档条目顺序、权限和时间固定，重复制作结果一致。需要 Windows 签名的资源，这一条作用在未签名的中间归档上，见“Windows 签名”。
- GPL 组件的源码压缩包与资源一起上传到 CDN 存档。
- 资源进入正式 catalog 前，必须拿到 [法务确认](../issues/preinstalled-tools/01-license-review.md) 的结论。开发和测试使用本地 loopback 资源服务，不受这一待办阻塞。
- 每个工具的版本由我们固定，用插件验收通过后写入 recipe。升级任何一项，都要使用新的 `resourceId` 并重新验收。各平台可以使用不同版本，差异记录在 recipe 中。
- 本期不自己编译任何资源。Windows 入口 shim 是 App 自己的代码，不属于资源。

### Windows 签名

Windows 11 的智能应用控制（SAC）在强制模式下会拦截没有可信签名、也没有云端信誉的 exe、dll 和 pyd。资源中由上游提供、但没有签名的 PE 文件，用 App 的代码签名证书签名。签名不改变程序的功能。

**范围**：每个 Windows 资源的 recipe 用 `windowsSigning` 声明。

| 值      | 含义                                    | 本期使用                                                                  |
| ------- | --------------------------------------- | ------------------------------------------------------------------------- |
| `zcode` | 签名步骤给资源中的 PE 文件签名          | Python、qpdf、Poppler                                                     |
| `none`  | 不签名。必须写 `reason`，制作时原样保留 | Pandoc（官方程序已签名）；LibreOffice（没有签名的文件，文档转换不会加载） |

没有 `windowsSigning` 的 Windows recipe，制作失败。

**签哪些文件**（`zcode`）：

- 前两个字节是 `MZ` 的文件，并且没有有效的 Authenticode 签名。判断依据是文件内容，不是扩展名。
- 已有有效签名的文件保留原签名，不重签，例如微软的 VC++ 运行库、Python Software Foundation 签名的文件。
- 非 PE 文件不送进签名工具。CI 曾把非 PE 文件交给签名工具，SafeNet token 进入坏状态，同一个 job 里后面的签名全部失败。
- recipe 可以用 `windowsSigning.exclude` 排除文件。每项写精确相对路径和原因，不允许通配符。只用于运行时会被复制并追加内容的模板文件，例如 pip 的启动器模板。追加内容会让签名失效，签名失效的程序比没有签名的程序更容易被拦截。声明的路径不存在、不是 PE 或已有有效签名时，签名步骤失败。是不是这类模板，由审阅 recipe 时核对。
- Windows 资源的 `rewrite` 不能指向 PE 文件。安装时改写会破坏签名，所以打包失败。

**流程**：

```text
recipe ──► 转换器（任意 Windows 制作机）
             │  执行全部打包检查
             ▼
           未签名的中间归档 + 中间资源描述
             │  制作两次，逐字节相同
             ▼
           签名步骤（CI 的 Windows 签名 runner，证书只在这里）
             │  1. 解开中间归档
             │  2. 逐个文件调用 scripts/sign-windows.ps1
             │  3. 签名后的校验
             │  4. 用固定的条目顺序、权限和时间重新打包
             ▼
           最终归档 + 最终资源描述 ──► 发布命令 ──► catalog 条目
```

- 中间归档和最终归档使用同一个 `resourceId`。只上传最终归档，中间归档不上传。
- 签名调用 `scripts/sign-windows.ps1`。签名规则、重试和时间戳回退与 App 安装包相同。
- 签名带时间戳，每次签名的结果都不同。最终归档不要求重复制作逐字节相同；可复现性由中间归档和下面的校验保证。

**签名后的校验**，任一项失败就不产出：

- 每个签过的文件，`Get-AuthenticodeSignature` 的状态为 `Valid`，并带时间戳。
- 同一资源内所有签过的文件，签名证书的指纹相同。时间戳回退规则如果换了证书，在这里失败。
- 去掉签名后，每个签过的文件与中间归档中的原文件逐字节相同。签名只能追加证书表，并修改 PE 头中的校验和与证书表目录项。
- 其他文件和目录与中间归档逐字节相同。`requiredFiles`、`entries`、`rewrite` 和 `runtimeChecks` 不变。
- 除 `exclude` 中的文件外，资源中不再有没有有效签名的 PE 文件。

**制作记录**：最终资源描述的 `provenance.windowsSigning` 记录：

- 中间归档的大小和 SHA-256；
- 签名证书的指纹；
- 签过的文件、保留原签名的文件和排除的文件，各自按路径排序。

**发布**：`windowsSigning` 为 `zcode` 的 Windows 资源，资源描述中没有 `provenance.windowsSigning` 时，发布命令拒绝生成 catalog 条目。

**安装**：预装进程只核对 catalog 中的 SHA-256，不检查 Authenticode 签名。安装不改写 PE 文件，所以签名在用户电脑上保持有效。

**签名解决不了的问题**：

- 企业的 AppLocker 或 WDAC 策略。不过，预装工具和 App 用同一张证书签名，企业按发布者放行 App 时，预装工具也一起放行。
- 第三方安全软件的隔离或提示。
- Defender 扫描新文件的时间。
- Python 附加区：Agent 后来用 pip 装的包，以及 pip 生成的命令启动器，都没有签名。在 SAC 强制模式下可能被拦截。

## 安全与隔离

- catalog 随 App 内置，不在运行时下载清单。下载内容以 SHA-256 为准。
- 安装和运行都不需要管理员权限，不写系统安装目录，不修改系统 PATH，不向系统字体目录安装字体，不修改用户的办公软件配置。
- 正式版、预览版、开发版各用独立的发布根，不共享在途操作。
- 抢先入口只影响 Agent 及其子进程，不影响用户自己的终端。用户可以按工具关闭“Agent 使用预装版本”。
- 预装不向 SSH、WSL、Docker 或独立 CLI 部署。Web 和手机不新增管理入口；手机控制本机任务时，仍使用本机的执行环境。

## 测试与验收

### 主验收切面

- 以桌面 E2E 为主要外部切面：从帮助菜单和真实 App 启动触发准备，观察 UI、下载请求、目录、入口和 Agent 命令的结果。测试只操作公开入口，不直接修改 store 或私有状态。
- 下载故障、慢速响应和并发请求使用现有的受控 HTTP 资源服务。小型测试资源只证明状态和交互；平台兼容、权限、字体、转换和公式重算必须使用真实资源。
- 不新增 App 业务单测。工程工具的行为改动先补回归测试，再改实现。

### 必要场景

以下是待实现的验收清单，不表示已有自动化覆盖。

### 现有候选的维护

下列待审核的桌面 E2E 候选按新合同改写，再改实现：`conversation-session-preinstalled-tools-{env,tracer,controls,faults,delete,release-isolation,clear-data,empty-catalog,startup,real-loopback,remote-context}`。`env` 改为断言入口目录与 PATH 顺序；`delete` 不再依赖调用标记；所有候选的状态断言改为按 `toolId` 读取。[用例目录](../conversation-session-case-catalog.md) 和覆盖矩阵同步更新。候选仍按 [E2E 用例生命周期](../../.agents/skills/e2e-case-lifecycle/SKILL.md) 推进，未经人工审核不转正。

所有候选的夹具都通过 `ZCODE_PREINSTALLED_TOOLS_CDN_BASE_URL` 把基址指向本地服务，catalog 只写 `archive.path`。这个变量在 App 启动时读取，同一个用例内不变。所以主／备候选用两个本地基址表示；代理与私有 CA 场景需要一个只能经代理访问的域名作为基址，单独放在 `conversation-session-preinstalled-tools-proxy` 候选中，不和 `faults` 共用一次启动。

### 工程测试

- 打包公共检查：Mach-O 最低系统版本、GLIBC、PE 架构、构建路径与重定位占位符、许可与来源文件，各自先有失败用例。上游路径豁免按 recipe 的前缀、已核对来源和原始文件逐字节一致性核对；把上游路径写进打包生成的文件、把本次打包环境路径写进任意文件，都必须拒绝。来源固定摘要核对可用于诊断路径和架构模板，两者共用同一份原始文件来源与摘要事实。
- PE 架构例外逐项核对精确路径、摘要、来源和用途；对禁止豁免的目标、摘要不符、路径不存在和不需要例外的文件，各有失败用例。不能按扩展名或非 Windows 平台整体跳过 PE 检查。
- `.pyc` 上游路径例外覆盖失败用例：前缀未出现在源码中、源码已改动、不同编译参数导致字节不一致、包含本次打包路径，以及其他生成文件包含上游路径。不能只靠 pyc 头部、手填摘要或布尔标记放行。
- catalog schema：重复 `toolId`、同平台多个资源、入口重名、入口目标不在必需文件中、不安全的 `archive.path`、完整地址或地域分组写法都被拒绝。下载地址按基址顺序生成，路径段经过 URL 编码。
- CLI：Bash 快照建立后创建入口，下一条命令能找到；删除入口后回到系统程序；PATH 顺序在快照后保持不变。
- 插件门禁：skills 中没有裸 `python` 或 `python3` 调用；四个文档插件中的统一入口和 profile 逐字节一致。

### 验证范围

- 开发阶段只在本机 macOS arm64 上做完整验证：代码检查、桌面 E2E、CLI 测试和真实资源全链路。
- 其他平台只做资源结构检查。Windows 入口、Git Bash PATH、x64 仿真和 Linux 运行，由人工或另起任务验证。完成前不宣称全平台完成。

## 实施顺序

实施票为 `docs/issues/preinstalled-tools/` 下的 02～14，依赖关系写在各票的“Blocked by”中。下面是对应的步骤：

1. 规格：本文、各工具规格、CLI 规格（本次）。
2. 契约与预装进程：catalog、记录和状态 schema 带 `toolId`；按工具分子树；每个工具一个 owner；串行队列；两个开关；入口派生；改写与重签；简化删除与清理；删除旧环境变量 `ZCODE_PREINSTALLED_TOOLS_RECORD` 及调用标记、删除门、删除意图记录。同时维护小包 E2E 候选。
3. 打包工具：抽出 `scripts/preinstalled-tools/common/`，迁移 LibreOffice 转换器；新增 Python、Poppler、Pandoc、qpdf 转换器；本机产出 macOS arm64 真实资源。
4. Host：注入 PATH 与 `ZCODE_PREINSTALLED_TOOLS_AVAILABLE`；Host 启动不再等待 Main 读取 catalog。
5. 插件：按各工具规格修改调用写法和统一入口，增加工程门禁，升版。
6. UI：多张卡片、开关、排队与升级文案、国际化。
7. 本机 macOS arm64 真实资源全链路验收，包括 Poppler 的中文 PDF 验收。

## 不在本期范围

- Node.js 与 npm 包，例如 docx、pptxgenjs、pdf-lib、playwright、sharp。下一期再做；本期的入口机制必须能直接覆盖它们。
- 插件写明“先问用户”的可选依赖：tectonic、Chromium；只在表格中提到、没有调用的 Ghostscript、tesseract；需要 tesseract 本体的 pytesseract。
- 主流程没有调用的 Python 包：markitdown、adjustText。
- PyMuPDF：法务不通过，不预装。用户需要时，按插件流程用预装 Python 安装到附加区，见 [Python 规格](python.md#附加区)。
- 独立的字体资源。LibreOffice 资源自带中文字体；插件现有的字体安装流程不变。
- 依赖解析、用户选择版本、在线 catalog、独立于 App 发布的更新。
- 放在 PATH 末尾的“兜底”入口方式。
- 接管 `python3`、`node` 这类带包环境的通用命令。
- 远端、Web、手机和独立 CLI 的部署与管理入口。
- 任务自动暂停、恢复和重发；断点续传。
- 修复文档插件已有的缺陷，见 [文档插件缺陷](../issues/document-plugin-defects/01-missing-html2pdf-script.md) 起的各张票。
